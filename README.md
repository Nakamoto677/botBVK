# BVK Support

Telegram-бот поддержки на Go и PostgreSQL. Клиенты пишут в личный чат, инженеры работают в топиках четырёх закрытых форум-групп: IT, 1С, Монтаж и Выезд.

## Ветки и зоны ответственности

| Ветка | Профиль агента | Содержимое |
|---|---|---|
| `main` | Рабочая основа | Проверенное объединённое приложение |
| `agent/database` | База данных | Миграции, PostgreSQL, inbox/outbox, архивные метаданные, черновики |
| `agent/tickets` | Бизнес-логика | Доступ, тикеты, права, назначения, передачи, рабочий календарь и метрики |
| `agent/telegram` | Telegram | Bot API, клиентский интерфейс, инженерные топики, доставка и восстановление |
| `integration/mvp` | Интеграция | Объединённое приложение, мониторинг, резервные копии, запуск и общие проверки |

Агенты работали в отдельных Git worktree. Изменения объединены через cherry-pick; общие модели лежат в `internal/domain`. Для дальнейшей работы создавать новые профильные ветки **от актуальной `main` или `integration/mvp`**, а не продолжать старые снимки. Профильные агенты не должны одновременно изменять общие контракты: изменение согласует интегратор. Удалённый репозиторий и отправка веток пока не настроены.

## Возможности

- Доступ клиента после одобрения администратором; одна открытая заявка на аккаунт.
- Постоянное меню с кнопками создания заявки, просмотра текущей заявки, истории и отмены.
- Новая заявка появляется только в теме «Очередь» выбранного отдела. Топик создаётся после «Взять в работу».
- Сообщения до назначения сохраняются и доставляются инженеру после создания топика.
- В карточках, топиках и сообщениях показываются имена клиентов из Telegram.
- Один исполнитель, переназначение, передача между отделами, ожидание клиента, закрытие, отмена и повторное открытие в течение семи дней.
- Требуемый режим переписки: обычные сообщения инженера в топике заявки автоматически доставляются клиенту, без Reply, `/reply` или предварительного нажатия кнопки. Статус реализации и критерии проверки описаны ниже.
- Сохранение текста, истории правок, событий и файлов до 20 МБ в независимом архиве. Альбомы сохраняются и доставляются отдельными элементами с общей отметкой альбома.
- Напоминания по календарю Пн–Пт 09:00–18:00 `Asia/Irkutsk`, настраиваемые часы и праздничные исключения. Приём сообщений круглосуточный.
- CSV-отчёт со сроками первого ответа, решения, ожидания клиента, передачами и повторными открытиями.
- Очередь повторных доставок, дедупликация Telegram updates, восстановление после перезапуска.
- Закрытие топика сразу; удаление через 30 дней только после проверки независимой резервной копии непосредственно перед удалением.

## Подготовка Telegram

1. Создать бота через BotFather и сохранить токен в `TELEGRAM_BOT_TOKEN`.
2. Создать четыре **закрытые супергруппы с включёнными темами**. В каждой создать постоянную тему «Очередь».
3. Сделать бота администратором с правами управления темами и удаления сообщений. Не включать анонимный режим у инженеров: действия привязываются к личным Telegram ID.
4. Внести ID групп, тем очереди, администратора и сотрудников в `config.json` по примеру `config.example.json`.
5. Администратор должен сначала открыть личный чат с ботом и нажать Start, чтобы бот мог отправлять ему личные уведомления.

Клиенты не входят в инженерные группы. Темы внутри группы не ограничивают видимость между её участниками: состав групп должен соответствовать разрешённому доступу к клиентским данным.

На тестовом боте ID группы/темы можно увидеть в `getUpdates`, отправив сообщение в нужную тему **до запуска polling приложения**. ID темы берётся из `message_thread_id`, группы — из `chat.id`; Telegram ID аккаунта — из `from.id`. Не запускайте отдельный `getUpdates` параллельно с рабочим ботом. При ранее установленном webhook удалите его перед использованием long polling, не сбрасывая накопленные updates.

## Быстрый запуск

Требуются Go 1.26 и PostgreSQL 17 или новее. Для проверки резервных копий установите PostgreSQL client tools (`pg_dump` и `pg_restore`) совместимой версии и добавьте их в PATH.

```powershell
Copy-Item config.example.json config.json
# Отредактируйте config.json: пример содержит вымышленные ID.
$env:DATABASE_URL = "postgres://bvk:CHANGE_ME@127.0.0.1:5432/bvk?sslmode=disable"
$env:TELEGRAM_BOT_TOKEN = "TOKEN_FROM_BOTFATHER"
./scripts/build.ps1
./bin/bvk.exe -config config.json -migrate
./bin/bvk.exe -config config.json -check
./bin/bvk.exe -config config.json
```

Создайте базу `bvk` и её пользователя заранее. `-migrate` создаёт таблицы и начальные компании/аккаунты; повторный запуск безопасен. Конфигурация сотрудников используется только для первоначального создания: она не отменяет отзыв доступа при рестарте. Изменение существующих сотрудников делайте через `/staff` и `/revoke`.

Токен и подключение к базе берутся из окружения; `.env` автоматически не читается. Не публикуйте реальные секреты и `config.json`. База, архив и копии содержат клиентские данные и требуют ограниченных прав доступа.

## Команды

| Кто | Команда | Действие |
|---|---|---|
| Клиент | `/start`, `/new` | Регистрация, выбор компании, создание заявки |
| Клиент/инженер | `/tickets`, `/history ID` | Доступные заявки и их история |
| Инженер | `/history` | История текущего топика |
| Исполнитель/диспетчер | `/reply текст` | Публичный ответ **ответом на сообщение клиента** |
| Исполнитель/диспетчер | `/close ID итог решения` | Закрыть заявку |
| Исполнитель/диспетчер | `/transfer ID 1c причина` | Передать в другой отдел; доступны `it`, `1c`, `installation`, `field` |
| Исполнитель/диспетчер | `/assign ID USER_ID` | Переназначить инженеру соответствующего отдела |
| Клиент/диспетчер | `/cancel ID причина` | Отменить заявку |
| Клиент | `/reopen ID` | Открыть свою закрытую заявку повторно |
| Диспетчер/администратор | `/report` | CSV-выгрузка |
| Администратор, личный чат | `/requests` | Необработанные заявки на доступ |
| Администратор, личный чат | `/staff USER_ID engineer it 1c` | Выдать инженерную роль и доступ к отделам |
| Администратор, личный чат | `/staff USER_ID dispatcher` | Выдать роль диспетчера |
| Администратор, личный чат | `/revoke USER_ID` | Отозвать доступ |
| Администратор, личный чат | `/bind TICKET_ID TOPIC_ID` | Привязать существующий топик при неизвестном результате создания |
| Администратор, личный чат | `/retry OPERATION_ID` | Вернуть неуспешную операцию в очередь |

Клиенту доступны постоянные кнопки меню. Инженер нажимает «Закрыть», затем пишет итог решения обычным сообщением; для передачи нажимает «Передать», выбирает отдел и пишет причину. Команды из таблицы остаются дополнительным способом управления.

## Требование: переписка как в обычном Telegram-чате

Клиент и инженер должны общаться привычным способом: написать сообщение или отправить вложение и нажать «Отправить». Бот передаёт сообщения между личным чатом клиента и топиком его заявки, а кнопки используются для управления заявкой.

- Сообщение клиента в личном чате автоматически попадает в топик его заявки; до назначения сохраняется для последующей доставки.
- Обычное сообщение исполнителя или другого сотрудника, имеющего право отвечать по заявке, в её актуальном топике автоматически отправляется клиенту. Reply на конкретное сообщение, команда `/reply` и кнопка «Ответить клиенту» для этого не требуются.
- То же правило действует для поддерживаемых вложений: фото, документов, голосовых сообщений, видео и подписей. Telegram Reply можно использовать по желанию; его отсутствие не препятствует доставке.
- Получатель определяется по заявке, привязанной к топику. Сообщения из общей очереди, постороннего или прежнего топика после передачи не должны уходить клиенту.
- Внутренняя заметка должна создаваться только через явно выбранное действие «Внутренняя заметка», с понятной отметкой, что клиент её не увидит. Обычные сообщения не являются внутренними заметками по умолчанию.
- Текст, введённый в явно начатом сценарии закрытия, передачи или внутренней заметки, обрабатывается этим сценарием и не отправляется как обычный ответ. Такой ввод привязывается к конкретному сотруднику и заявке; остальные сотрудники продолжают обычную переписку.
- Ошибка доставки должна быть видна сотруднику; интерфейс не должен сообщать об успешной доставке до подтверждения Telegram. Проверки доступа, история сообщений и очередь повторных доставок сохраняются.

**Статус:** это согласованное требование к доработке, а не подтверждение готовой реализации. Прежний сценарий с обязательной кнопкой «Ответить клиенту» или `/reply` не соответствует требуемому поведению. Код и тесты необходимо привести к этому разделу.

**Критерии приёмки:** двумя Telegram-аккаунтами проверить создание и назначение заявки, отправку инженером обычного текста и вложений без Reply и `/reply`, получение их клиентом и ответ клиента в том же топике. Дополнительно проверить явную внутреннюю заметку, отсутствие пересылки служебного ввода и сообщений из старого топика после передачи, запрет ответа без прав, повторную доставку после временной ошибки и сохранность переписки после перезапуска.

При первом обращении или после одобрения доступа появится меню; если старая переписка уже открыта, нажмите Start или `/menu`.

После передачи заявка появляется в очереди нового отдела; его топик создаётся только после «Взять в работу». Повторное открытие также возвращает заявку в очередь до назначения. Старые карточки не дают права действовать над заявкой в прежнем отделе. Пока топик создаётся, повторная передача блокируется. Если Telegram ответил неопределённо при создании темы, автоматическое повторное создание запрещается: проверьте группу, используйте `/bind`, затем `/retry`. Инженер может ответить на начальную карточку без дополнительного сообщения клиента.

При обновлении остановите старый процесс/службу, замените исполняемый файл и запустите новую версию. Миграции применяются автоматически: сохраняется история, старые карточки обновляются. Старые настройки служебного чата и дежурств игнорируются; в новом примере конфигурации их нет.

## Windows-служба

Скрипт `scripts/install-service.ps1` использует [NSSM](https://nssm.cc/usage). Запускайте установку из PowerShell администратора; NSSM должен лежать по постоянному пути.

```powershell
./scripts/install-service.ps1 `
  -NssmPath "C:\Tools\nssm.exe" `
  -InstallDir "C:\BVKSupport" `
  -DatabaseUrl $env:DATABASE_URL `
  -TelegramToken $env:TELEGRAM_BOT_TOKEN
```

Перед `Start-Service BVKSupport` назначьте отдельную служебную учётную запись и права на каталог данных; проверьте доступ к PostgreSQL и `-check`. Логи направлены в `data/logs`, служба перезапускается при выходе приложения. Скрипт не устанавливает PostgreSQL или NSSM и не запускает службу автоматически.

Пилот допускает один активный экземпляр. Второй процесс с той же базой завершится с ошибкой. Блокировка держится выделенным соединением PostgreSQL; потеря соединения останавливает обработчики. Это ещё не режим высокой доступности с полноценным fencing: второй физический хост, репликация базы и общее хранилище — следующий этап.

## Резервные копии и мониторинг

В `backup_dir` задайте каталог **на другом физическом носителе или сервере**, доступный служебной учётной записи. Путь архива и путь копий должны быть отдельными каталогами.

```powershell
./bin/bvk.exe -config config.json -backup
```

Команда делает custom-format dump, восстанавливает его во временную БД, копирует и сверяет вложения по SHA-256, затем создаёт `manifest.json` с подтверждением проверки. Для этой команды подключение должно быть URL `postgres://...`, а используемый аккаунт иметь право создавать и удалять временные базы. Можно запускать backup под отдельным PostgreSQL-аккаунтом с необходимыми правами; рабочему боту право `CREATEDB` не требуется.

Настройте ежедневный запуск `scripts/backup.ps1` в Планировщике заданий Windows под отдельной учётной записью с `DATABASE_URL` в защищённом окружении и PostgreSQL tools в PATH. Само приложение не регистрирует задачу на вашем сервере. При ошибке проверки manifest не выдаётся и автоматическое удаление топиков блокируется.

Отдельно храните конфигурацию и секреты в защищённой резервной копии. Архив сообщений не очищается автоматически до утверждения политики хранения. Копии можно хранить 30 дней; не удаляйте последнюю проверенную копию. Ежемесячно проверяйте полное восстановление на отдельном компьютере.

- `/live` — процесс запущен.
- `/ready` — база отвечает, Telegram polling актуален, очередь не зависла и нет неуспешных операций.
- `/metrics` — размер очереди, число ошибок и возраст старой исходящей операции.

По умолчанию HTTP слушает `127.0.0.1:8080`. Для внешней проверки используйте агент мониторинга на Windows или отдельный адрес в защищённой внутренней сети; endpoints не имеют собственной авторизации и не предназначены для публичного Интернета. Внешняя проверка должна работать на другом компьютере и уведомлять администратора при отказе. Неуспешная доставка может также отражать блокировку бота клиентом; это требует разбора, а не бесконечного автоматического повтора.

## Тесты

```sh
go test -race ./...
go vet ./...
docker compose -f compose.test.yml up -d
TEST_DATABASE_URL='postgres://postgres:bvk-test-only@127.0.0.1:55432/bvk_test?sslmode=disable' go test -race -count=1 ./...
```

Для проверки настоящего dump/restore добавьте PostgreSQL tools в PATH и `TEST_BACKUP_TOOLS=1`. Тест резервного копирования создаёт и удаляет собственные временные базы; тесты хранилища и общего цикла используют изолированные схемы. Используйте тестовую базу.

Без `TEST_DATABASE_URL` интеграционные проверки PostgreSQL пропускаются. Telegram тестируется локальным HTTP-сервером; реальный токен в тестах не используется.

## Границы первой версии

- MAX и автоматические проверки клиентских серверов пока не подключены.
- Нельзя вести вторую самостоятельную открытую заявку одного клиента: новую проблему сначала координирует диспетчер; выделение параллельных связанных тикетов требует изменения этого правила.
- Файлы больше 20 МБ пересылаются, но не включаются в независимый архив; соответствующий топик не удаляется автоматически.
- Замена медиа через редактирование требует отправки нового файла отдельным сообщением. Событие такой правки блокирует автоматическое удаление, чтобы не потерять заменённое вложение.
- История содержит сообщения, которые получил бот. Удаление пользователем сообщения не гарантированно приходит как событие; простой более 24 часов может потерять входящие Telegram updates.
- При неизвестном результате сетевой отправки возможны повторы сообщений. Принятые в БД сообщения сохраняются независимо от результата доставки.
- Отчёт показывает время реакции/решения; это не учёт трудозатрат инженеров.
- Реальный Telegram-пилот и проверка службы на Windows требуют токена, рабочих ID и доступа к вашему серверу.

Ограничения Telegram: [Bot API](https://core.telegram.org/bots/api), [лимиты и polling](https://core.telegram.org/bots/faq). Резервные копии: [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).
