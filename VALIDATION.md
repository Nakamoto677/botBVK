# Проверка реализации — 12 октября 2026

Проверено на macOS arm64, Go 1.26.5, с временным PostgreSQL 17 в Docker. Рабочий Telegram-токен не использовался.

## Успешные проверки

- `go test -race -count=1 ./...` с `TEST_DATABASE_URL` и `TEST_BACKUP_TOOLS=1`: прошли все 55 тестовых функций, включая интеграционные проверки, без пропусков тестов БД/резервной копии.
- `go vet ./...`: ошибок нет.
- Сборка `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath`: получен `bin/bvk-windows-amd64.exe`.
- Профильные ветки `agent/database`, `agent/tickets`, `agent/telegram` отдельно собираются и проходят собственные тесты с окончательными общими контрактами.
- Штатная команда `go run ./cmd/bvk -config config.example.json -migrate` проверена на тестовой БД.

## Что покрыто

- Одновременное создание активной заявки и назначение инженера, откат транзакции, уникальность источника сообщения.
- Inbox/outbox, восстановление аренды операции, сохранение очередности, повтор неуспешной доставки и единые часы PostgreSQL.
- Одобрение доступа, сохранение настроек при рестарте, черновики, правки исходных сообщений и их принадлежность закрытому тикету.
- Права клиента, инженера и диспетчера; изоляция истории компаний и отделов; отчёты только в разрешённых чатах.
- Строгий `/reply`, ответ на первое описание, подтверждённая доставка первого ответа, ошибки Bot API и отсутствие токена в сообщениях ошибок транспорта.
- Полный цикл на настоящей БД и тестовом HTTP Bot API: регистрация → назначение → сообщения до/после передачи → ответ → закрытие → повторное открытие.
- Рабочие часы Иркутска, выходные, напоминания, аварийные уведомления и отсутствие дежурного.
- Настоящий `pg_dump`/`pg_restore` во временную БД, независимая копия файла, SHA-256, обнаружение испорченного дампа.
- Блокировка удаления при правке сообщения после формирования копии, повторная проверка под блокировкой тикета, повторное планирование отложенного удаления.

## Ещё требуется на рабочем окружении

1. Заполнить реальные ID и секреты, проверить права и темы через `-check`.
2. Провести пилот в настоящих Telegram-группах: реальные медиа, перезапуск, блокировка бота клиентом и снятие прав.
3. Проверить службу Windows и права служебной учётной записи; нативный запуск на Windows здесь не выполнялся.
4. Назначить диспетчера/дежурных, ежедневную задачу резервирования и внешнюю проверку `/ready`.

Временная тестовая БД не содержит рабочих клиентских данных. Подключение MAX и резервирование на втором физическом хосте остаются отдельными этапами согласованного плана.
