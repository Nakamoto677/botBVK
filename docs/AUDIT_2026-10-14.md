# Аудит системы BVK Support — 14 октября 2026

Проверены код приёма и доставки сообщений, формы, служебные действия, PostgreSQL,
блокировки, миграции, планировщик, архивирование и удаление, аналитика, права доступа,
история и обработка ошибок. Особый приоритет — серии сообщений и задержки.
Исправления находятся в рабочем дереве; действующий бот и рабочая БД не обновлялись.
Это аудит исходников и воспроизводимых сценариев на отдельной БД, а не измерение
нагрузки действующего сервера или гарантия отсутствия всех возможных ошибок.

## Найдено и исправлено

| Проблема | Причина и последствие | Исправление |
|---|---|---|
| P1: потеря предыдущих частей описания | Каждое сообщение формы заменяло `Draft.Text` | Последовательное добавление абзацев; ID исходных сообщений защищают от повторного добавления после сбоя |
| P1: пропуск файлов в серии | Вложение без подписи отклонялось до сохранения | Сохраняются все поддерживаемые вложения, в том числе до текстового описания; подача всё ещё требует текст |
| P1: аналитика задерживала приём | Analytics Refresh брал эксклюзивный advisory lock `731903`, тот же, что разделяется при сохранении входящих сообщений | Аналитика использует отдельный `731904` |
| P1: взаимная блокировка пользователей и заявки | Assign/Reopen брали блокировку второго пользователя после строки заявки; другой обработчик мог держать пользователя и ждать эту заявку | Пользователи блокируются по возрастанию ID до блокировки заявки |
| P1: потеря входящего действия при deadlock | SQL `40P01`/`40001` превращались в бизнес-конфликт, после которого inbox отмечался завершённым | Сохраняется тип ошибки PostgreSQL; действие повторяется без карантина и ложного сообщения клиенту |
| P1: глобальная задержка при проверке копии | Хеширование дампа/файлов выполнялось уже под общей блокировкой приёма | Общая блокировка берётся после проверки копии; перед удалением повторно проверяется незавершённый inbox |
| P1: сетевое ожидание под блокировкой заявки | Replay накопленных сообщений держал транзакцию во время rate limit, чтения прогресса отправки и HTTP | Отправка вне транзакции; проверка текущего маршрута до отправки и запись фактического назначения после; закрытие/удаление остаются за этой операцией в outbox |
| P1: заимствование второго соединения внутри транзакции | BeforeDelete вызывал Store.Events/Messages при уже занятом соединении; несколько таких задач могли исчерпать небольшой пул | Чтение истории через ту же транзакцию |
| P2: случайное совпадение системной и пользовательской блокировки | Telegram ID использовался как положительный ключ в том же пространстве, что системные номера | Ключи пользователей — отрицательные ID; системные номера остаются положительными |
| P2: повтор мог ждать до 50 секунд | Проверка inbox и long polling находились в одном цикле | Приём и обработка разделены; обработка пробуждается по сигналу и проверяет повторы каждые 100 мс |
| P2: медленная отправка мешала другим клиентам | Один последовательный исходящий Worker | До четырёх независимых операций одновременно; общий ограничитель частоты и порядок по заявке/беседе |
| P2: задержки в личном чате | Для личных чатов использовались групповые 3,1 с; clientNotification дополнительно ожидал дважды | 1,1 с между отправками в личный чат, 3,1 с в группу, без двойного ожидания; общий интервал 35 мс |
| P2: устаревшие подтверждения после серии сообщений | Для каждой промежуточной версии описания создавался экран | Небольшое окно 350 мс для подтверждения; устаревшие ещё не отправленные версии пропускаются, актуальность проверяется и после ожидания лимита |
| P2: повтор нажатия создания сбрасывал форму | `/new` всегда создавал новый черновик | Существующая незавершённая форма возобновляется |
| P2: лишние обновления карточки | Каждое дополнение создавало новый refresh | Ожидающие обновления объединяются; уже исполняющееся обновление не поглощает последующее изменение |
| P2: стоимость выбора inbox росла с историей | Функция зависимостей повторялась для пар записей, сравнения использовали текстовые преобразования индексированных ID | Вычисление ключей один раз на незавершённую запись, числовые сравнения и частичные индексы |
| P2: ложная ошибка при повторе принятого сообщения | Повтор INSERT после успешного сохранения и сбоя подтверждения давал conflict | Для уже сохранённого источника, автора и заявки повтор считается принятым |

При введении параллельной доставки отдельно добавлена защита: активная операция
не выбирается повторно после истечения её пятиминутной аренды. После перезапуска
просроченные операции по-прежнему восстанавливаются. Это рассчитано на существующий
режим одного активного процесса бота; защита `731902` сохранена.

## Карта клиентских состояний после исправлений

| Состояние | Ввод и результат |
|---|---|
| Без доступа | Выбор компании → запрос администратору → одобрение/отказ |
| Главное меню | «Создать заявку», «Помощь» |
| Выбор отдела | Четыре отдела и отмена формы; повтор создания возобновляет форму |
| Описание | Одно/несколько сообщений, файлы и альбомы; части добавляются по порядку |
| Только вложения | Вложения сохранены, бот просит текст описания |
| Подтверждение | Актуальный общий текст и число вложений; «Отправить» / отмена; старые кнопки не подают другой вариант |
| Активная заявка | Новые сообщения идут в ту же заявку; до назначения сохраняются для последующей доставки |
| Отмена/закрытие | Существующие подтверждения, архивирование и домашнее меню |
| История | Права на заявку/файл перепроверяются, служебные сообщения скрыты от клиента |

Схемы callback_data, четыре отдела, одна активная заявка, нижние клавиатуры,
сохраняемые семь типов клиентских сообщений и правила удаления истории сохранены.
Меняется смысл повторного текста формы: он дополняет описание. Чтобы начать
описание заново, отмените форму и создайте новую; `/start` также сбрасывает форму.
Уже отправленные сохраняемые подтверждения не удаляются: подавляются только
устаревшие экраны, которые ещё находятся в очереди.

Используется собственный Go-клиент Bot API без стороннего Telegram SDK. Новых
возможностей клиента Telegram не требуется. Текущая документация проверена
14.10.2026: [Bot API](https://core.telegram.org/bots/api) и
[ограничения отправки](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## Что проверено

Отдельный PostgreSQL 18.6: `127.0.0.1:57439`, каталог
`/private/tmp/bvk-audit-20261014-pg`. Тестовые схемы и базы изолированы;
Telegram заменён HTTP-моками. Рабочие секреты, сообщения и БД не использовались.

Новые регрессии проверяют:

- серию текстов и файлов, фото без подписи, сохранение после перезапуска,
  повтор того же update, один актуальный предпросмотр, итоговую подачу;
- повторное `/new` без потери текста и повтор принятого сообщения без дубля;
- повтор через две секунды во время продолжающегося long poll;
- медленный HTTP в одном чате, независимую отправку другому и FIFO внутри беседы;
- отсутствие двойного ожидания первой отправки и влияния ожидания группы на личный чат;
- единый порядок UI и уведомлений заявки; объединение refresh только до начала исполнения;
- разделение системных/пользовательских блокировок и блокировки аналитики;
- порядок блокировок Assign/Reopen, повтор SQL deadlock вместо потери действия;
- отсутствие блокировки заявки во время HTTP replay;
- чтение архивной истории в той же транзакции и проверку копии до общей блокировки;
- идемпотентную миграцию с сохранением заявок и ожидающих операций;
- запрет повторного выбора ещё работающей операции с просроченной арендой;
- обработку 100 упорядоченных записей inbox при 10 000 завершённых исторических строках.

Последний синтетический замер выбора/подтверждения 100 записей: **50,35 мс**.
Это время PostgreSQL на данном Mac, без бизнес-обработчиков и Telegram;
оно не является обещанием задержки ответа пользователя.

Команды проверки и итоговый результат — [VALIDATION.md](VALIDATION.md).
Сквозной тест включает регистрацию, заявку с файлом, переписку и исправления,
передачу, закрытие, настоящий dump/restore, проверку копии, удаление,
получение файла и повторное открытие.

## Ограничения и следующие наблюдения

1. **Лимиты Telegram остаются.** Для одной группы Telegram указывает 20 сообщений
   в минуту, для одного чата рекомендует не превышать одно сообщение в секунду.
   Обходить ограничения дополнительными горутинами нельзя. При `429` операция
   повторяется с учётом `retry_after`; итоговая скорость зависит также от сети.
2. **Последний шаг удаления всё ещё защищён общей блокировкой.** Она нужна, чтобы
   не удалить топик с ещё не сохранённым исправлением. Сетевой вызов удаления
   ограничен пятью секундами вместо общего HTTP timeout 65 с; тайм-аут оставляет
   удаление для безопасного повтора. Хеширование больше не держит общую блокировку,
   но блокировка конкретной заявки на время проверки копии остаётся.
3. **Входящие обработчики остаются последовательными.** Обычная переписка быстро
   сохраняет действия в outbox; редкие прямые операции `/report`, выдача файла
   истории и административная проверка `/bind` ещё могут задержать применение
   следующих входящих действий во время HTTP/диска. Приём Telegram в durable inbox
   теперь продолжается отдельно. Для полной изоляции этих команд нужен отдельный
   контракт фоновой выдачи файлов с повторной проверкой прав, прогрессом и дедупликацией;
   эта переработка в текущие исправления не включена.
4. **Четыре занятых исходящих обработчика — ограниченная очередь.** Четыре долгие
   независимые операции могут задержать пятую. Бесконечная параллельность увеличила
   бы нагрузку и число `429`, поэтому ограничение намеренное.
5. **Большая история:** список заявок/история читают данные целиком, планировщик
   обходит историю, аналитика пересчитывает полный снимок. Сейчас отделена её
   ошибочная блокировка, но CPU/диск/память остаются общими ресурсами. Для оценки
   длительной эксплуатации нужны реальные объёмы и нагрузочные замеры сервера;
   SQL-пагинация и инкрементальная аналитика — отдельные последующие изменения.
6. **Карантин inbox:** зависимые действия и удаление блокируются до разбирательства.
   Автоматически объявлять такой update успешным небезопасно. Новая панель
   восстановления карантина не добавлялась; `/ready`/`/metrics` пока не показывают
   его отдельным показателем. Диагностический SQL ниже показывает карантин.
7. **Неизвестный исход Telegram:** если сервер принял сообщение, а ответ потерялся,
   повтор иногда может дать дубль. Подтверждённые части сохраняются; абсолютная
   exactly-once доставка внешнего API не обещается.
8. **Файлы свыше доступного Bot API размера** не имеют независимой локальной копии;
   такое завершение не должно разрешать удаление топика. Существующая защита сохранена.

Настоящий Telegram-пилот двумя аккаунтами, сетевые замеры работающего бота и
нативный запуск Windows-службы не выполнены. Проверка безопасности здесь —
проверка прикладных прав/данных и существующих регрессий, не пентест инфраструктуры.

## Внедрение и диагностика блокировок

При следующем плановом обновлении остановить старые процессы бота и аналитики,
создать проверенную копию, собрать и обновить оба бинарника, затем запустить.
Миграция `008_burst_delivery` применяется штатным Migrate. Она добавляет столбец,
индексы и функцию выбора зависимостей, заполняет связи ожидающих операций;
не удаляет заявки, историю, файлы и архивы. Старую и новую версии одновременно
не запускать: меняются ключи advisory locks и схема исходящей очереди.

Для наблюдения именно в момент задержки добавлен
[`scripts/diagnose-locks.sql`](../scripts/diagnose-locks.sql). Он только читает:
блокирующие PID, тип ожидания, возраст транзакции, назначение системных блокировок,
карантин и состояния очередей. Тексты сообщений и SQL-запросов не выводятся.
Запускать на нужной БД через штатную защищённую настройку подключения `psql`;
не вставлять пароль в команду или отчёт. Отсутствие блокировок в один момент
не исключает кратковременных ожиданий ранее.
