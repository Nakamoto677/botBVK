# BVK Support — актуальное состояние системы

Единственный источник правды по устройству, эксплуатации и открытой работе.
Заменяет прежние 12 файлов документации (README, PLAN, VALIDATION, CLIENT_UI,
ENGINEER_UI, AUDIT, ANALYTICS_*, METABASE, LOCAL_ANALYTICS, AGENT_RELIABILITY_UX).
Сверено с кодом коммита `b7a672e`, 16 октября 2026.

Правила работы над проектом — в [AGENTS.md](AGENTS.md).

## 0. Что сделать при следующем запуске

**Автозапуска нет: после перезагрузки бот и аналитика не поднимутся сами.** Проверено
16 октября — в `~/Library/LaunchAgents` и `launchctl` записей для них нет, процессы
запускались вручную из терминала. Сами поднимаются только `bot-bvk-postgres-1` и
`bvk-metabase-local` (у них политика Docker `unless-stopped`). То есть после включения
машины нужно запустить бота и `bvk-analytics` руками, иначе Telegram не опрашивается,
а аналитика не обновляется.

**Запущенный бот может работать на устаревшем коде.** Правки, сделанные 16 октября
(пустая клавиатура, классификация ошибок, автоуборка мёртвых операций, флаг
`-skip-telegram-check`), вступают в силу **только после перезапуска**: работающий
процесс держит в памяти свою сборку.

Проверить и обновить:

```sh
cd /path/to/bot-BVK
curl -s -o /dev/null -w '%{http_code}\n' https://api.telegram.org   # должен быть не 000
go build -trimpath -o bin/bvk ./cmd/bvk
kill <PID старого процесса>          # или Ctrl+C в его терминале
export TELEGRAM_BOT_TOKEN='…'
nohup ./bin/bvk -config config.json > /tmp/bvk-run.log 2>&1 &
sleep 3 && curl -s localhost:8080/ready

# аналитика обновляет снимок для Metabase, отдельный процесс
nohup ./bin/bvk-analytics -config config.json > /tmp/bvk-analytics.log 2>&1 &
```

Точка отката, если новый запуск не устроит: `cp /tmp/bvk-previous bin/bvk` (может не
пережить перезагрузку — тогда пересобрать из коммита `7726520`).

Проверить, что запущена свежая сборка, можно по флагу — он добавлен последним:

```sh
./bin/bvk -h 2>&1 | grep -q skip-telegram-check && echo "свежая сборка" || echo "СТАРАЯ сборка"
```

Замеры в `/metrics` (`bvk_ratelimit_wait_ms_*`, `bvk_operation_s_*`) для этой проверки
**не годятся**: они добавлены раньше и присутствуют в сборке от 13:21.

## 1. Что это

Один Telegram-бот технической поддержки. Клиент общается в личном чате.
Сотрудники работают в четырёх закрытых форум-группах: **IT, 1С, Монтаж, Выезд**
(коды `it`, `1c`, `installation`, `field`); в каждой заранее создана тема
«Очередь» (`queue_topic_id`).

Поток обработки:

```
getUpdates → Adapter → durable inbox → handlers + tickets.Service
           → транзакция PostgreSQL + outbox → Worker → Telegram / архив
           → Scheduler: напоминания, проверка копии, удаление
```

Стек: **Go 1.26**, PostgreSQL, `pgx/v5` 5.7.6, собственный HTTP-клиент Bot API.
Ни Telegram SDK, ни ORM, ни Redis, ни брокера, ни веб-панели нет. Часовой пояс
бизнес-логики — **Asia/Irkutsk (UTC+8)**, рабочий календарь Пн–Пт 09:00–18:00.

## 2. Роли и права

| Роль | Доступ |
|---|---|
| Неодобренный | Выбор компании, запрос доступа; заявки недоступны |
| `client` | Одна активная заявка, сообщения в неё, отмена, своя история, повторное открытие в пределах 7×24 ч |
| `engineer` | Заявки разрешённых отделов: взятие, публичные ответы, передача; закрытие и смена исполнителя — только для назначенных на него |
| `admin` | Все отделы, все операции, управление доступом, `/report` |
| `dispatcher` | Привилегированная роль в коде; диспетчерского чата и аварийной маршрутизации **нет** — остаток совместимости |

Присутствия в Telegram-группе недостаточно: проверяются сохранённый пользователь,
роль, одобрение и отдел. Сообщения от анонимных админов (`sender_chat`), других
ботов и служебные события групп не становятся ответами клиенту. `/revoke` не
отзывает физический доступ к уже существующей группе.

## 3. Клиентский поток

**Регистрация.** `/start` → доступные для регистрации компании → выбор создаёт
`client` без одобрения и запрос в `bvk_access`. Админу уходят кнопки
«Одобрить»/«Отклонить», очередь — `/requests`. Принадлежность к компании проверяет
человек; интеграции с каталогом нет. Повторный `/start` не меняет компанию.

**Создание заявки.** Домашние кнопки: «Создать заявку», «Помощь». Форма: отдел →
описание → «Отправить»; на каждом шаге «Отменить подачу заявки». Нужен текст или
подпись; поддерживаемый файл сохраняется в черновике и переносится в заявку
атомарно. Последовательные сообщения **дополняют** описание, а не заменяют его;
вложения принимаются без подписи; повторы не дублируют. `/form` возобновляет
черновик после перезапуска. **Одна активная заявка** на аккаунт, независимо от
отдела (проверка сервисом и индексом `bvk_active_client`).

Ответ: «Заявка принята!\nВ ближайшее время в этот чат вам ответит специалист)».
Заявка получает статус `new`, карточку в теме «Очередь» отдела и **отдельного
топика не создаёт**. Дополнения клиента сохраняются до взятия.

**Отмена.** «Отменить заявку» → «Точно проблема решена?» → «Да, завершить» /
«Нет, продолжить». Причина не запрашивается. Статус `cancelled`. Ответ:
«Рады, что ваша проблема решилась)\nОбращайтесь в любое время, мы всегда рады
помочь!». Подтверждение действует 15 минут; повтор старого не завершает заявку.

**Список, карточка, история, повторное открытие.** `/tickets` — по 10 на страницу,
устойчивый порядок, «Назад»/«Далее». `/ticket ID` — карточка. `/current` —
активная. `/history ID` работает и после удаления топика, порциями. Права
проверяются при каждом переходе и каждой выдаче файла. Повторно открыть можно
**только `closed`** (не `cancelled`): клиенту — в течение 7×24 ч после закрытия и
при отсутствии другой активной заявки; `admin`/`dispatcher` без ограничений.
Заявка возвращается в очередь своего отдела без исполнителя и топика; новое
взятие создаёт **новый** топик.

## 4. Инженерный поток

**До назначения.** Карточка: номер, статус, компания, имя и Telegram-ник клиента,
отдел, исполнитель, описание. Кнопки «Взять в работу», «Передать». Конкурентные
взятия сериализуются — назначается один исполнитель.

**После взятия.** Статус `in_progress`, сохраняются исполнитель и **новое
поколение маршрутизации**, затем через outbox создаётся топик. Пока идёт
подготовка, действия скрыты и передача заблокирована. Клиент получает: «Инженер
[имя] взял вашу заявку в работу\nВаша переписка продолжится прямо в этом чате:».
Имя берётся из профиля при нажатии, иначе username, иначе «поддержки».

**Переписка.** Обычный текст или поддерживаемый файл **любого одобренного
инженера текущего отдела** в актуальном топике автоматически уходит клиенту.
Reply, `/reply`, кнопка ответа и спецрежим не нужны. Клиент отвечает в личном
чате, бот доставляет в актуальный топик с именем клиента. Сообщения очереди,
чужих и прежних топиков публичными ответами не являются. Успешная отправка не
создаёт отдельного подтверждения.

**Передача.** Доступна любому одобренному инженеру текущего отдела, включая
неназначенного, либо `admin`/`dispatcher`; работает и до взятия. «Передать» →
другой отдел → причина текстом или подписью («-» — без комментария, пустой ввод
не принимается). Текущий отдел не предлагается. Результат: отдел и статус `new`,
исполнитель сброшен, прежняя привязка топика сброшена, в прежний топик уходит
«Передано в отдел …», карточка создана в новом отделе, клиент уведомлён.
Причина публично не пересылается. Новый топик — только после следующего взятия.
**Передача сама по себе не запускает удаление прежнего топика.**

**Закрытие и смена исполнителя.** Закрывает назначенный исполнитель или
`admin`/`dispatcher`; нужен итог следующим сообщением. Клиент получает «Заявка
закрыта. Результат: …». В топик перед закрытием — «Тикет закрыт инженером»;
подтверждённая отправка фиксируется событием `topic_closing_notice`, повтор
операции не отправляет сообщение дважды. При клиентской отмене это сообщение не
отправляется. `/assign TICKET_ID ENGINEER_ID` — для `in_progress`/`waiting_client`,
новый топик не создаётся.

Служебный ввод закрытия и передачи хранится в БД, действует 15 минут и изолирован
по сотруднику, чату и топику; вложение шага архивируется с направлением `service`.

## 5. Статусы

| Код | Значение | Переходы |
|---|---|---|
| `new` | В очереди, без исполнителя | взятие → `in_progress`; передача → `new` другого отдела; отмена → `cancelled` |
| `in_progress` | В работе | ожидание → `waiting_client`; передача → `new`; закрытие → `closed`; отмена → `cancelled` |
| `waiting_client` | Ожидает клиента | ответ клиента автоматически → `in_progress`; возобновление, передача, закрытие, отмена |
| `closed` | Закрыта с итогом | допустимое повторное открытие → `new` |
| `cancelled` | Завершена отменой | повторное открытие не реализовано |

Активны первые три. `RoutingPending` — технический признак подготовки топика, не
бизнес-статус. **`waiting_client` частично скрыт:** сервис, callbacks `waiting`/
`resume`, авто-возобновление и напоминания работают, но текущие клавиатуры кнопок
ожидания не создают и команды `/waiting` нет.

## 6. Сообщения, файлы, история

Поддерживаются текст, документы, фото, голосовые, видео, аудио с подписями.
Стикеры, контакты, геолокации и видеокружки отдельно не обрабатываются.
`media_group_id` сохраняется, но элементы альбома идут по одному, без
`sendMediaGroup`.

Направления: `inbound` (клиент), `outbound` (публичный ответ инженера), `service`
(вложение служебного шага), `internal` (историческая заметка; **создание новых
отключено**, значение только читается).

**Независимый архив.** Файлы до **20 MiB** скачиваются в
`archive_dir/<ticket_id>/<message_id>.bin` с SHA-256. Большие могут пересылаться
по `file_id`, но остаются без независимой копии и **блокируют удаление топика**.
Локальный Bot API server не подключён. Архивирование идёт **до** доставки, поэтому
временная ошибка скачивания или диска может задержать отправку.

**Редактирование** сохраняет предыдущие версии. Правка клиента в активной заявке →
инженерам «Исправление сообщения …». Правка публичного ответа → клиенту
«Исправление ответа» с цитатой. Замена вложения редактированием пишет
`media_edit_unsupported`, оставляет исходный файл и **блокирует автодаление**;
готового сценария снятия блокировки нет.

**История.** `/history` показывает текст, переписку, прежние версии, итог
последнего закрытия, имена сторон, время Иркутска, вложения и состояние копий.
Клиенту доступны только `inbound`/`outbound`: `internal`, `service`, их подписи,
имена файлов и revisions полностью скрыты. Кнопка вложения повторно проверяет
права; локальный файл выдаётся после проверки SHA-256 и принадлежности архивному
каталогу, путь из callback не принимается.

## 7. Завершение, архив и удаление

Для нового закрытия или отмены с существующим топиком сохраняется намерение
`completion_cleanup_requested` с ключом из ID заявки, поколения маршрутизации,
chat ID и topic ID. Далее семь шагов:

1. Завершение сохраняется транзакционно, топик временно закрывается.
2. Фоновый цикл проверяет завершение принятых доставок и архивирования,
   отсутствие необработанных updates и сохранность файлов.
3. Полный `database.dump` в custom format через `pg_dump`.
4. Дамп **действительно восстанавливается** через `pg_restore` во временную БД
   `bvk_verify_*` на том же сервере.
5. Файлы копируются и сверяются по SHA-256, создаётся `manifest.json` с checksum
   дампа и покрытием сообщений и событий.
6. Проверяется покрытие конкретного завершения, в outbox ставится `delete_topic`.
7. Перед удалением — повторная проверка под блокировкой, согласованной с приёмом
   updates. Уже отсутствующий топик считается успешно удалённым.

Цикл запускается при старте и далее примерно раз в минуту, резервирование
последовательно. **Копия включает всю БД, а не одну заявку.** Удаление
откладывается при недоступном архиве, незавершённой доставке, неподдерживаемой
замене медиа, изменившихся данных или ошибке копии. Админ получает причину, после
устранения бот продолжает автоматически, повторяющаяся причина не уведомляет
каждую минуту.

**Исключения.** Завершение без топика не создаёт намерение удаления и не запускает
копию. Топики, закрытые передачей, в удаление последнего топика не включаются.
Исторические закрытия массово не удаляются.

Копии: `backup_dir/<UTC timestamp>/` с `database.dump`, `manifest.json`, `files/`.
Автоматической ротации нет, разные пути не проверяются на разные физические диски,
конфигурация и секреты в копию не входят, отдельной команды полного восстановления
рабочего приложения нет — автовосстановление служит только проверкой копии.

## 8. Напоминания и отчёт

Планировщик при старте и раз в минуту:

| Условие по умолчанию | Получатель |
|---|---|
| Нет первого ответа 30 рабочих минут от создания | Отдел |
| Нет активности инженера 4 рабочих часа в `in_progress` | Отдел |
| `waiting_client` длится 2 рабочих дня (18 рабочих часов при 9–18) | Клиент |

Автозакрытия по молчанию клиента нет. `FirstResponseAt` ставится после успешной
доставки первого публичного сообщения инженера клиенту, а не после взятия или
системного уведомления.

`/report` — CSV `tickets.csv` по всем заявкам без фильтра периода: ID заявки,
компании и клиента, отдел, статус, исполнитель, время создания, первого ответа и
закрытия, закрывший, итог; календарные и рабочие секунды реакции, решения и
ожидания; число передач, повторных открытий, закрытий инженером и отмен. Текст
итога защищён от интерпретации как формула. Агрегированного экрана статистики в
боте нет.

| `/quarantine clear ID` | `admin`: вернуть карантинный update в обработку |

Автоматической регистрации команд через `setMyCommands`, настройки menu button и
обработки `/start` с payload нет. Неизвестная команда ведёт в справку. При
неизвестном результате создания топика автоповтор **запрещён** (защита от дубля):
админ проверяет группу, делает `/bind`, затем `/retry`.

## 10. Запуск и эксплуатация

### Требования

- Go 1.26; PostgreSQL; `pgx/v5` 5.7.6.
- `pg_dump` и `pg_restore` в PATH процесса, совместимые с сервером; рабочему
  пользователю PostgreSQL нужны права на чтение и **создание временных БД**.
- Один токен Telegram, четыре разные форум-группы, тема очереди в каждой.
- Бот — админ групп с `can_manage_topics` и `can_delete_messages`.
- Сотрудники заранее начинают личный чат с ботом.
- Каталог архива и **отдельный** каталог копий, желательно на независимом носителе.

### Секреты

Только из окружения: `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`. В `config.json` их быть
не должно.

### config.json

Копировать из `config.example.json`. **Неизвестные настройки отклоняются.**
Относительные пути становятся абсолютными относительно рабочего каталога процесса.

| Поле | Назначение и значение по умолчанию |
|---|---|
| `admin_id` | Telegram ID базового администратора |
| `companies` | Каталог регистрации: объекты `id`, `name` и опциональный `legacy_name`; старый массив строк совместим. `[]` отключает регистрацию, отсутствие или `null` — ошибка |
| `staff` | Начальные ID, имена, роли и отделы сотрудников |
| `departments` | Все четыре ключа, для каждого `chat_id` и `queue_topic_id` |
| `archive_dir` | `data/archive` |
| `backup_dir` | `data/backups` |
| `health_address` | `127.0.0.1:8080` |
| `start_hour`, `end_hour` | `9`, `18` |
| `holidays` | Даты `YYYY-MM-DD`, по умолчанию нет |
| `first_response_minutes` | `30` рабочих минут |
| `idle_hours` | `4` рабочих часа |
| `waiting_days` | `2` рабочих дня |

Специально игнорируются: `dispatcher_chat_id`, `topic_retention_days`, вложенный
`duty_user_id`. Bootstrap **добавляет отсутствующих** сотрудников, но не
синхронизирует существующие роли и отделы с JSON на каждом старте. Каталог
компаний синхронизируется при каждом старте. `/staff` и `/revoke` не могут
изменять базовый `admin_id`.

### Сборка и флаги

```sh
go build -trimpath -o bin/bvk ./cmd/bvk
./bin/bvk -config config.json -migrate
./bin/bvk -config config.json -check
./bin/bvk -config config.json
```

| Флаг | Что выполняет |
|---|---|
| `-config PATH` | Путь к JSON, по умолчанию `config.json` |
| `-migrate` | Миграции и bootstrap, выход; токен не требуется |
| `-check` | Также миграции и bootstrap; проверяет БД, токен, группы и права, выходит |
| `-backup` | Копия с настоящим восстановлением; бот не запускается |
| `-skip-telegram-check` | Старт без **удалённой** проверки прав Telegram (см. ниже) |

**Флаг `-skip-telegram-check` нужен, когда сеть блокирует Telegram.** Обычный старт
делает `getMe`, затем `getChat` и `getChatMember` по каждому отделу — примерно десять
сетевых вызовов **до** запуска обработчиков, и при недоступном Telegram любой из них
валит запуск целиком. С флагом эти проверки пропускаются, поэтому валидный бот
поднимается и на заблокированной сети, начиная опрашивать сам, как только сеть
отпустит.

Что при этом **остаётся** обязательным: `TELEGRAM_BOT_TOKEN` и локальная форма
конфигурации — все четыре отдела, положительные `chat_id` и `queue_topic_id`, разные
группы. То есть опечатку в конфиге флаг не пропустит, а вот отсутствие прав у бота в
группах — да, и это выяснится только при первом действии.

Обычный старт тоже применяет миграции и bootstrap, затем проверяет Telegram и
запускает обработчики. **`-check` не read-only:** меняет схему и начальные записи
и не проверяет обмен сообщениями, наличие темы очереди и готовность backup tools.

### Синхронизация компаний без потери данных

Миграция `007_company_sync` добавляет стабильный ключ и флаг доступности
регистрации. Числовые ID записей, пользователи, запросы, заявки, сообщения,
события, архивные пути и файлы сохраняются; компании не удаляются.

```json
"companies": [
  {"id": "bvk", "name": "Новое название БВК", "legacy_name": "Точное прежнее название из БД"},
  {"id": "new-company", "name": "Новая компания"}
]
```

- `id` — постоянный ключ (1–64 символа: латиница, цифры, `_`, `-`). При
  переименовании менять **только** `name`.
- `legacy_name` — явный переход с прежней записи; указывать **точное название из
  БД**. При первом связывании источник должен быть ровно один, иначе откатывается
  весь каталог. После успеха поле можно убрать.
- Объект без `legacy_name` создаёт новую организацию, если `id` неизвестен.
- Старый массив строк поддерживается: идентичная строка сохраняет компанию,
  изменённая считается заменой.
- Исключение элемента отключает **только новую регистрацию**: одобренные клиенты
  сохраняют доступ, заявки, переписку и историю.

Порядок применения: остановить бот и сохранить копию → выгрузить
`SELECT id, name FROM bvk_companies ORDER BY id;` → перевести переименования в
объекты с `id` и точным `legacy_name` → `./bin/bvk -config config.json -migrate` с
прежним `DATABASE_URL` → `-check` → запуск. **Не запускать старый бинарник после
обновления схемы:** его bootstrap зависит от уникальности имени.

### Singleton и advisory-локи

Выделенное соединение держит PostgreSQL advisory lock **731902**, проверяет каждую
секунду; при потере соединения рабочие циклы останавливаются. Это защита пилота, а
не высокая доступность: fencing, репликации и авто-failover нет, и лок в одной БД
не защищает два сервера с разными восстановленными БД.

| Ключ | Назначение |
|---|---|
| `731901` | Миграции (`pg_advisory_xact_lock`) |
| `731902` | Singleton бота |
| `731903` | Приём updates (shared) и финальное удаление топика (exclusive) |
| `731904` | Аналитика — отдельный, чтобы не блокировать приём |

Ключи пользователей — **отрицательные** ID, чтобы не совпадать с системными.

### Health endpoints

Без авторизации, по умолчанию только на loopback.

| Endpoint | Поведение |
|---|---|
| `/live` | HTTP 200, пока HTTP-сервер отвечает |
| `/ready` | HTTP 503 при отсутствии свежего polling более 2 минут, недоступной БД, `failed` в outbox, возрасте самой старой операции более 5 минут или **непустом карантине updates** |
| `/metrics` | `bvk_outbox_pending`, `bvk_outbox_failed`, `bvk_outbox_oldest_seconds`, `bvk_updates_quarantined` и замеры этапов (см. ниже) |

`/ready` не проверяет восстановление копий и внешние зависимости; внешний
мониторинг процесса подключать отдельно.

**Замеры этапов.** `/metrics` отдаёт гистограммы с фиксированными границами
(память не растёт с трафиком): ожидание лимитера по методу API
(`bvk_ratelimit_wait`), время Telegram по методу (`bvk_telegram_call`),
длительность операции по виду (`bvk_operation`) и время от записи сообщения до
его доставки (`bvk_ticket_relay`). Для каждой серии есть `_bucket`, `_count`,
`_sum`, `_max`, `_mean`. Эти метрики и позволили найти реальные причины
задержки вместо догадок.

отдельная установка PostgreSQL, его tools и NSSM.

## 11. Аналитика

### Процесс

`cmd/bvk-analytics` использует календарь и пороги из `config.json` бота, но **не
требует токена Telegram** и не запускает миграции бота. Публикует снимок при
старте и далее раз в минуту, попытка ограничена 55 секундами. Флаги: `-once` —
один снимок и выход; `-migrate` — только создать или обновить аналитическую схему
и выйти (выполняет владелец БД, в службу не передавать).

Чтение пяти исходных таблиц идёт пакетно в транзакции **REPEATABLE READ**;
метаданные сообщений читаются без текста и файлов; строки аналитики заменяются
через DELETE/COPY в той же транзакции. Сбой откатывает весь снимок, предыдущая
версия остаётся доступной читателям. Частичные снимки не публикуются. Между
независимыми SQL-карточками Metabase во время публикации возможны соседние целые
снимки — для строгой ручной сверки остановить расчётчик.

### Схема `analytics`

| Таблица | Содержание |
|---|---|
| `analytics.tickets` | Текущее состояние, клиент, компания, первое назначение, признаки внимания |
| `analytics.cycles` | Циклы, результат и автор завершения, календарные и рабочие сроки |
| `analytics.events` | События и исторические участники |
| `analytics.state_intervals` | Статус, отдел и назначенный во времени |
| `analytics.employees`, `companies`, `departments` | Справочники; клиенты не входят в сотрудники |
| `analytics.refresh_state` | Время снимка, версия, число неполных заявок, последняя ошибка |

Полная переписка, файлы, исходный JSON, пути архива и токен в витрины не
публикуются. Карточка заявки не обращается к Telegram-топику.

**Правила расчёта.** Цикл начинается созданием или повторным открытием.
Завершение берётся из события, автор — `ActorID`. При нескольких закрытиях
последняя операция внутри периода выбирается до фильтра сотрудника или отдела.
Первый ответ — подтверждённая доставка исходного публичного `outbound`-сообщения
внутри цикла; исправления, служебные сообщения и неудачные отправки исключаются.
Отдел ответа фиксируется на момент доставки, отдел закрытия — на момент закрытия.
Срок заявки — от создания до закрытия; срок сотрудника — от последнего назначения
до закрытия, включая ожидание, ночи и выходные. Неизвестные сроки исключены из
среднего и максимума.

### Metabase: карточки и фильтры

**51 карточка, пять вкладок:** Обзор, Требуют внимания, Сотрудники, Подробно, Как
читать. Обзор — четыре главных показателя и сравнение с предыдущим интервалом той
же длительности. Сотрудники — фактические авторы последних закрытий, текущая
нагрузка, сроки. Требуют внимания — без исполнителя, просроченный первый ответ,
простой инженера, все активные по возрасту. Нажатие номера открывает карточку
заявки с циклами, результатами и историей.

Порядок фильтров: начало и конец периода, отдел, сотрудник, компания. Пустые даты
означают текущий месяц по Иркутску. Дни включаются целиком, правая граница — начало
следующего дня или время снимка. Блоки «Сейчас» и внимания не ограничиваются
периодом. Смысл сотрудника зависит от карточки: поступления — первое назначение,
закрытия — последний закрывший, ответ — действительно ответивший, текущая очередь
— назначенный сейчас. Счётчик и его список построены на одном SQL-наборе, суммы
строк совпадают со счётчиками. Нулевой предыдущий показатель даёт абсолютную
разницу без окраски «хорошо/плохо».

### Развёртывание

- Панель только через loopback: `http://localhost:3000/dashboard/1#refresh=60`.
- Контейнер `bvk-metabase-local`, образ `metabase/metabase:v0.64.1.x`.
- База настроек Metabase — отдельная `bvk_metabase` в том же PostgreSQL; учётные
  записи прикладной БД и читателя аналитики различаются. Источник Metabase —
  **только** схема `analytics`.
- Локальный источник — БД `bvk_test` контейнера `bot-bvk-postgres-1` на
  `127.0.0.1:55432`.
- Локальные пароли в `data/metabase-local/ACCESS.md` (вне Git, каталог 0700).
- Логи: `data/metabase-local/analytics.log`, `docker logs bvk-metabase-local`.


прежнюю домашнюю страницу в `data/metabase-local/ui-before-*.json`, затем
пересобирает manifest; ручные правки управляемой раскладки при импорте
заменяются.

### Импорт карточек на другой сервер

```sh
python3 analytics/metabase/build.py
python3 analytics/metabase/import.py --database-id 1 --dry-run
python3 analytics/metabase/import.py --url http://127.0.0.1:3000 --database-id 1 --validate-queries
python3 -m unittest discover -s analytics/metabase -p 'test_*.py'
```

Импортёр спрашивает email и пароль админа интерактивно либо берёт
`METABASE_API_KEY`/`METABASE_SESSION` из окружения; пароль не сохраняется.
Нужен Python 3 и только стандартная библиотека. **Сохранять `import-state.json`**
вместе с установочными материалами: повторный импорт обновляет объекты, а без
прежнего state создаётся новый комплект. Удалённый импорт требует HTTPS, HTTP
разрешён только на loopback. Используется REST API OSS, не платная serialization.

### Грабли, ломающие повторное развёртывание

1. API Metabase запрещает пустую строку описания — импортёр передаёт NULL.
2. Параметр запроса должен содержать ID — добавлен стабильный ID template-tag.
3. Начальное описание топика доставляется как `source_message_id=0`,
   `initial_description=true`; это штатная служебная доставка, а не пробел
   истории, иначе `incomplete_count` становится ненулевым.
4. Потеря `import-state.json` создаёт новый комплект вместо обновления.
5. Потеря encryption key Metabase делает восстановленную БД нерасшифровываемой.
   Минимум 32 случайных байта в Base64, хранить отдельно.
6. Отдельная прикладная БД обязательна; H2 не используется.
7. Пароли ролей задавать только интерактивным `\password` в psql.
8. `ALTER DEFAULT PRIVILEGES` привязан к роли, выполняющей provision; при другом
   владельце повторить `GRANT ... FOR ROLE` и после каждой миграции выдавать
   права на новые таблицы.
9. `provision.sql` рассчитан на новые свободные имена ролей.
10. PostgreSQL суммирует права, включая PUBLIC: GRANT скрипта не отменяет ранее
    выданных PUBLIC прав. Запускать `check-privileges.sql`, проверить
    SECURITY DEFINER функции и `pg_hba.conf`.
11. `company_sync.sql:5` создаёт уникальный индекс без `IF NOT EXISTS`.
12. Установщик служб отказывается работать с заглушками в
    `scripts/analytics/versions.json`; зависимости он не скачивает.
13. `icacls` не удаляет все старые явные записи при непустом каталоге.
14. Metabase требует Java 21+ и запуск JAR с
    `--add-opens java.base/java.nio=ALL-UNNAMED`.
15. Не открывать наружу 3000, 2019, 5432, 8080. Порты 80 и 443 — только для
    ACME и HTTPS.

### Роли PostgreSQL

| Роль | Разрешения |
|---|---|
| `bvk_analytics_writer` | SELECT пяти `public.bvk_*` (`tickets`, `messages`, `events`, `users`, `companies`); SELECT/INSERT/UPDATE/DELETE в `analytics` |

Порядок: владелец исходной БД применяет `bvk-analytics -config config.json
-migrate`, затем администратор PostgreSQL выполняет

затем три разных случайных пароля через `\password`. Ни один runtime-пользователь
аналитики не должен владеть исходной БД или таблицами, иметь SUPERUSER, CREATEDB,
CREATEROLE, членство в широких ролях или CREATE в исходной схеме.

### Windows-развёртывание аналитики

Рекомендуемый каталог `C:\BVKAnalytics`: `bin\bvk-analytics.exe`, `bin\caddy.exe`,
`java\bin\java.exe`, `metabase\metabase.jar`, `config.json`, `Caddyfile`,
`versions.json`, `run-service.ps1`, `secrets\*.json`, `data\logs\`.

```powershell
./scripts/analytics/install-services.ps1 -InstallDir 'C:\BVKAnalytics' -NssmPath 'C:\Tools\nssm.exe'
Start-Service BVKAnalytics ; Start-Service BVKMetabase ; Start-Service BVKCaddy
```

Создаются три остановленные службы с виртуальными учётными записями
`NT SERVICE\BVKAnalytics`, `NT SERVICE\BVKMetabase`, `NT SERVICE\BVKCaddy`. Если
конкретная Windows или NSSM не принимает виртуальную запись, используется
отдельная служебная запись без административных прав и переназначение ACL.
Установщик отключает наследование ACL каталога и secrets, оставляет полный доступ
Administrators и SYSTEM, даёт runtime чтение неизменяемых файлов и запись только в
свои логи. NSSM перезапускает упавший процесс с задержкой 10 секунд — это не
внешний мониторинг. Секреты лежат на диске в открытом виде под ACL, поэтому нужен
BitLocker и копии на зашифрованном носителе; в Git их быть не должно.

```json
{"DATABASE_URL":"postgres://bvk_analytics_writer:URL_ENCODED_PASSWORD@127.0.0.1:5432/bvk?sslmode=disable"}
{"MB_DB_HOST":"127.0.0.1","MB_DB_PORT":"5432","MB_DB_DBNAME":"bvk_metabase","MB_DB_USER":"bvk_metabase_app","MB_DB_PASS":"REPLACE","MB_ENCRYPTION_SECRET_KEY":"REPLACE_WITH_RANDOM_BASE64","MB_SITE_URL":"https://support.example.org"}
{"ANALYTICS_DOMAIN":"support.example.org","ACME_EMAIL":"admin@example.org"}
```

`sslmode=disable` приемлем только для loopback; при отдельном PostgreSQL нужен TLS
с проверкой сертификата. Проверка Caddy: `caddy.exe validate --config
C:\BVKAnalytics\Caddyfile --adapter caddyfile`.

## 14. Тесты и проверки

### Прогон восстановления копии (делать перед боем и после изменений схемы)

`bvk -backup` — это **не просто создание дампа, а настоящий прогон восстановления**:
он снимает `pg_dump --format=custom`, создаёт временную БД `bvk_verify_*`,
восстанавливает туда дамп через `pg_restore --exit-on-error`, читает оттуда заявки и
сообщения, сверяет SHA-256 каждого архивного вложения, пишет `manifest.json` с
`verified: true` и **удаляет временную БД**. Ошибка на любом шаге валит команду
ненулевым кодом.

```sh
cd /path/to/bot-BVK
export DATABASE_URL='postgres://…/bvk'        # рабочая база
./bin/bvk -config config.json -backup
# ожидаемый вывод:
#   INFO backup restored and verified directory=…/data/backups/<UTC>
```

Требования: `pg_dump` и `pg_restore` в PATH **той же мажорной версии, что сервер**
(или новее в пределах совместимости), и право `CREATE DATABASE` у рабочего
пользователя. Флаг не применяет миграции, но создаёт и удаляет временную БД, поэтому
рабочую базу он только читает.

Проверено 16 октября 2026 на рабочей базе: 94 заявки, 137 сообщений (137 хешей
сверено), 3 архивных вложения, `verified: true`, временная БД удалена. Совпадение с
источником полное.

Что делать с результатом: `data/backups/<UTC>/` содержит `database.dump`,
`manifest.json` и `files/`. **Копировать эту папку на независимый носитель** —
автоматической ротации и выгрузки нет. Копия включает **всю БД**, не одну заявку, и
не включает `config.json` и секреты.

Отдельного флага «восстановить рабочую БД из копии» нет намеренно: это
разрушительная операция, её выполняют вручную (`pg_restore` в целевую БД при
остановленном боте).

```sh
go vet ./...
go test -race -count=1 ./...

docker compose -f compose.test.yml up -d
TEST_DATABASE_URL='postgres://postgres:bvk-test-only@127.0.0.1:55432/bvk_test?sslmode=disable' \
  TEST_BACKUP_TOOLS=1 go test -race -count=1 ./...

TEST_ANALYTICS_LOAD=1 go test -count=1 -run TestFiveYearRefresh -v ./internal/analytics
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o bin/bvk-windows-amd64.exe ./cmd/bvk
python3 -m unittest discover -s analytics/metabase -p 'test_*.py'
git diff --check
```

**`TEST_DATABASE_URL` обязателен:** без него все тесты БД **молча
пропускаются**, и `go test ./...` зелёный без покрытия персистентности.
`TEST_BACKUP_TOOLS=1` вместе с `pg_dump` и `pg_restore` в PATH включает проверки
копирования. `TEST_ANALYTICS_LOAD=1` — нагрузочный сценарий аналитики.
`internal/postgres` создаёт временную схему и ставит `search_path`;
`internal/integration` создаёт целую БД и требует `CREATE DATABASE`;
`internal/archive/restore_test.go` дополнительно требует backup tools.
**Не задавать производственный DSN** для полного набора.

Telegram в тестах заменён локальным HTTP-сервером; `Client.BaseURL` и `Client.HTTP`
экспортированы — это и есть тестовый шов интерфейса.

Порты, которые нельзя путать: **55432** — рабочая и тестовая БД бота,
**55433** — прежняя изолированная проверка, **56439** и **57439** — изолированные
PostgreSQL 18.6, **55439** — проверка синхронизации компаний, **3000** — Metabase,
**3001** — drill, **2019** — админ-API Caddy, **8080** — health бота.

Покрыто: доступ и одна активная заявка, конкурентное назначение, дедупликация
входящих, FIFO outbox, восстановление аренды, отмена без причины, устаревшие
кнопки и поколения формы, сохранение черновика после перезапуска, атомарная подача
и rollback при конфликте вложения, прозрачные ответы инженеров отдела, запрет
публикации служебного и внутреннего, права и выдача файлов с SHA-256, пагинация
истории без дублей и пропусков, длинные тексты с emoji, серии сообщений и
альбомов, медленный HTTP в одном чате и независимость другого, разделение
системных и пользовательских локов, порядок блокировок Assign и Reopen, повтор SQL
deadlock, отказ от повторного выбора работающей операции по истёкшей аренде,
миграции 005–008 с сохранением старых данных и сквозной цикл от регистрации до
копии, удаления, истории и повторного открытия.

Ориентиры производительности (не производственные): выборка 100 записей inbox при
10 000 завершённых — 50,35 мс; сквозной `internal/integration` — около 130 с;
полный расчёт аналитики на синтетике 73 000 заявок — 3,03 с на Apple M5 с
локальной PostgreSQL 18.6.

## 15. Решения, которые нельзя отменять

Явно удалено и не восстанавливается без нового требования пользователя:

- **Аварийная маршрутизация и диспетчерский чат.** Роль `dispatcher` остаётся
  принимаемой, но отдельного сценария нет.
- **Режим внутренних заметок.** Создание новых отключено; направление `internal`
  читается только для старых архивных записей и никогда не рассылается.
- **Обязательные reply-контролы.** Переписка прозрачна, без Reply, `/reply` и
  кнопки ответа.
- **Тридцатидневная очистка.** Удаление топика допускается только после проверенной
  копии конкретного нового завершения. Миграция отключает старые операции
  массового удаления, **сохраняя их записи для аудита**.

Прочие правила:

- Одна активная заявка клиента; четыре отдела; топик создаётся только после
  «Взять в работу»; передача возвращает заявку в очередь.
- Новая заявка попадает только в очередь, без отдельного топика.
- Обычные ответы всех одобренных инженеров текущего отдела публичны; закрытие — по
  правам исполнителя.
- Отмена без причины; повторное открытие только `closed` в текущих границах.
- Сохранять нижние клавиатуры и семь типов `client_kept`.
- Удаление топика блокируется необработанным inbox, незавершённой доставкой или
  архивированием, изменившимся архивом и неподдерживаемой заменой медиа.
- Старые записи, переписка, архивы и политика удаления должны пережить миграции
  без потери данных.
- Перед интерфейсными правками применять навык `.agents/skills/telegram-bot-ui`;
  явные требования пользователя выше навыка.
- Exactly-once при неизвестном сетевом исходе Telegram не обещается и не должно
  заявляться.
- «Настоящий Telegram-пилот» и «нативная Windows-служба» пишутся отдельно от
  HTTP-моков и cross-build; не заявлять выполненными без фактического запуска.

## 16. Известные дефекты и открытая работа

### Исправлено: пустая клавиатура теряла экраны и карточки (16 октября)

**Самый серьёзный дефект, найденный на живой базе.** В рабочей базе лежало
**16 операций** со статусом `failed` и одной ошибкой Telegram:

```
telegram 400: Bad Request: field "inline_keyboard" must be of type Array
```

Причина видна в сохранённом payload: `markup={"inline_keyboard": null}`.
Проверка отсекала только литеральную строку `"null"`, а объект с `null` вместо
массива пропускала, и Telegram отвергал **весь запрос**. Ответ `400` считается
постоянной ошибкой, поэтому операция помечалась мёртвой и экран или обновление
карточки терялись навсегда.

Источник: `engineerTopicButtons` и `engineerQueueButtons` возвращают **пустой**
список кнопок, когда заявка неактивна или топик ещё готовится, а `Markup{Buttons:
nil}` сериализовался в `{"inline_keyboard": null}`.

Исправлено в двух местах, чтобы не повторилось:

1. `Markup.MarshalJSON` не выводит поле, когда ни в одной строке нет кнопок. Пустая
   клавиатура теперь означает «нет inline-кнопок», а не невалидную.
2. Очередь экранов отправляет клавиатуру только если это объект, реально
   содержащий строки. `null`, пустой список, пустой объект и битый JSON поле
   опускают, поэтому сообщение доходит, а не теряется целиком.

Покрыто тестами на все четыре пустые формы и на настоящую клавиатуру.

**Эксплуатация `failed`: есть автоматическое снятие.** `failed` в outbox —
**терминальное** состояние, а `/ready` отдаёт `503` при `failed > 0`. То есть одна
мёртвая операция раньше навсегда переводила бота в «не готов», и исправить это мог
только человек.

Теперь на том же минутном тике планировщика работает уборка
(`Store.RetireFinishedFailures`), которая снимает **только то, что нельзя осмысленно
повторить**:

- операция по заявке, которая уже **закрыта или отменена** — доставлять больше нечего;
- операция **без заявки** (так выглядит экран) старше **15 минут**.

**Что намеренно остаётся видимым:** failure по **живой** заявке — любой давности,
потому что там клиент или инженеры всё ещё ждут, и скрывать это нельзя; а также
операция со ссылкой на **несуществующую** заявку — это признак проблемы с данными,
а не шум. Причина сохраняется в `last_error`, каждое снятие пишется в лог (операция,
вид, заявка).

Мёртвые операции были также сняты вручную 16 октября — тот же безопасный критерий,
только по завершённым заявкам:

```sql
UPDATE bvk_outbox o SET state='done', lease_until=NULL,
       last_error='снято вручную: причина устранена, цель завершена'
WHERE o.state='failed'
  AND NOT EXISTS (SELECT 1 FROM bvk_tickets t
                  WHERE t.id=o.ticket_id AND t.status IN ('new','in_progress','waiting_client'));
```

После этого `/ready` вернулся в `200`, `failed` = 0, карантина нет.

### Исправлено: устаревший экран молча оставлял индикатор (16 октября)

`boundDraft` при устаревшем черновике возвращал `valid=false` вместе с `nil`
ошибкой (`internal/telegram/drafts.go`), поэтому вызывающие ветки считали выход
успешным: callback не подтверждался и у пользователя оставался вращающийся
индикатор. Найдено при разборе `Adapter.callback`.

Теперь устаревший экран возвращает `domain.ErrConflict`, а признак
`Adapter.answeredCallback` не даёт `respondError` переотвечать на callback и
перекрывать понятное объяснение «Этот экран больше не актуален…». Ответ приходит
ровно один раз, спиннер не зависает, форма не меняется.

**Это изменение видимого поведения:** нажатие устаревшей кнопки раньше
завершалось «успешно» и молча, а теперь считается отклонённым действием. Тесты,
закреплявшие прежнее поведение
(`TestStaleDraftCancelAndDepartmentCannotAffectActiveTicket`,
`TestRetainedButtonsCannotMutateAnotherForm`,
`TestDraftFileReplacementRestartSubmitAndStaleScreens`), обновлены: устаревшие
экраны в них теперь явно проверяются как `ErrConflict`, а валидные — как успех.
Регрессия — `TestStaleDraftAnswersCallbackOnceWithExplanation` в
`internal/telegram/spinner_test.go`.

### Приоритет: скорость взятия и жизненный цикл топиков

Симптомы пользователя: взятие заявки занимает около пяти секунд; удаление топиков
при завершении и передаче ведёт себя непредсказуемо.

Причины найдены в коде:

- `Worker.interval` = 3,1 с применяется к любому запросу в группу, включая
  создание топика и служебные сообщения, а не только к новым сообщениям.
- `deleteForumTopic` вызывается **внутри** `Transact` под эксклюзивной блокировкой
  `731903`, которую каждый входящий update берёт shared.
- `close_topic` порождается в трёх независимых местах с разными payload
  (передача, завершение, отмена), плюс `delete_topic` из планировщика и правки
  состояний прямо в SQL миграций `queue_on_claim.sql` и `completion_cleanup.sql`.
- Планировщик просыпается по таймеру 100 мс.

План: замеры базовых показателей; короткий путь взятия с немедленным
подтверждением callback; ограничитель по назначению запроса вместо общего
интервала; независимые последовательности доставки; единая сохраняемая запись
топика с состоянием `создание → активен → закрытие → закрыт → проверка копии →
удаление → удалён` и один компонент на каждую операцию; вынос ожидания HTTP и
файловых операций из транзакций подготовки топика.

**Сделано 16 октября.** Замеры добавлены, две причины устранены, эффект измерен
на воспроизводимой базовой линии (`TestClaimBaselineBreakdown`: мок Telegram с
задержкой 250 мс, боевой интервал 3,1 с, четыре параллельных слота очереди):

| Показатель | До | После |
|---|---|---|
| Клиенту сообщили о взятии | 21,1 с | **1,1 с** |
| Топик готов для инженеров | 14,7 с | 5,9 с |
| Ожидание лимитера | 13,9–19,6 с | ~5,1 с |
| Время Telegram HTTP | 1,5 с | 1,5 с |

Что устранено:

- Интервал на чат платили **все** вызовы в группу, включая `editMessageText`,
  `createForumTopic` и `closeForumTopic`, которые нового сообщения не добавляют.
  Теперь интервал платит только метод, публикующий сообщение; общий интервал 35 мс
  и обработка `retry_after` сохранены.
- `conversation_id` вычислялся как `client_id` заявки **для всех** видов операций,
  поэтому подготовка топика попадала в полосу клиентского чата и держала
  уведомление клиента за собой. Теперь полосу получают только виды, реально
  добавляющие сообщение в чат. Порядок внутри чата сохранён.
- Попутно найдены два латентных дефекта: сравнение `conversation_id` считало
  `0 = 0` совпадением, из-за чего операции без чата блокировали друг друга;
  и `notify_client` стоял в общей полосе заявки.
- Убрана лишняя работа в подготовке: клавиатура инженера ставилась **до**
  `replayDeferred`, из-за чего служебная подсказка обгоняла ждавшие сообщения, а
  `refresh` затем проверял её повторно вторым запросом событий. Теперь клавиатура
  ставится один раз в конце. Дало 5,87 → 5,62 с.

**Инвариант сохранности сообщений покрыт тестами.** Сообщение, отправленное
раньше готовности топика, сохраняется в БД с `DeferredDelivery` и доставляется
`replayDeferred` после подготовки, ровно один раз. Покрыто с обеих сторон:
написанное **до** взятия и пришедшее **внутрь окна подготовки** (связь с топиком
уже записана, подготовка ещё идёт) — `TestMessageWrittenBeforeClaimIsDeliveredByTopicSetup`
и `TestMessageArrivingDuringTopicPreparationIsDeliveredAfterwards`. Оба проверяют
точное число доставок, сохранение имени автора и завершение подготовки.

**Параллелить обновление карточек не нужно.** Топик заявки создаётся в том же
`chat_id`, что и очередь отдела, то есть это **одна группа** с одним лимитом
Telegram. Поэтому лимитер и так сериализует карточку очереди и карточку топика;
параллельная отправка не дала бы выигрыша, а две одновременные записи в заявку
конфликтуют на версии и уходят в повтор с задержкой 1–2 с, то есть медленнее
последовательного варианта. Заготовка была написана и отброшена по этой причине.

**Удаление топика: граница проверена, но переделка требует отдельного замысла.**
Удаление идёт внутри транзакции, держащей эксклюзивную блокировку `731903`, а её
на каждом входящем апдейте берут shared. То есть медленный Telegram останавливает
приём **для всех чатов**. Граница в 5 с (`topicDeleteTimeout`) была, но ничем не
проверялась — теперь покрыта тестом, который требует, чтобы запрос нёс бюджет
блокировки, а не 65-секундный таймаут HTTP-клиента; проверка идёт через транспорт,
потому что `httptest`-сервер не получает дедлайн вызывающего. Второй тест
закрепляет правило, делающее повтор безопасным: топик, о котором Telegram сообщает
как об отсутствующем, считается удалённым.

Вынести сетевой вызов из-под блокировки **нельзя простой правкой**: между
проверкой «нет необработанных апдейтов» и самим удалением сообщение может быть
принято и осиротеть — топик уже удалён, доставить некуда. Это ровно тот случай
потери сообщения, который требуется исключить. Правильное решение — отдельный
замысел: пометить топик как ожидающий удаления, закоммитить намерение, удалять вне
блокировки и уметь отменить удаление при повторном открытии.

**Осталось по этому плану:** склейка трёх `editMessageText` на карточку в один шаг,
единая запись топика с явными состояниями, вынос ожидания HTTP из транзакций
подготовки, и описанный выше замысел по удалению. Отдельно требует решения
пользователя самое дорогое: из четырёх групповых сообщений на взятие одно —
служебная подсказка «сообщения уходят клиенту», которая нужна только чтобы показать
нижнюю клавиатуру. Её перенос на inline-кнопки карточки экономит целый интервал
Telegram, но убирает постоянные нижние кнопки у инженеров. Симптом «топики то
удаляются, то нет» **не проверялся** после этих правок.

### Как снять живой замер (требует токена, автоматически не снимается)

Базовая линия выше получена на моке с задержкой Telegram 250 мс. Живой замер
нужен, чтобы проверить это допущение и увидеть реальные значения:

```sh
cd /path/to/bot-BVK
export TELEGRAM_BOT_TOKEN='…'
go build -trimpath -o bin/bvk ./cmd/bvk
./bin/bvk -config config.json            # оставить работать

# в другом терминале, после двух-трёх взятий заявки инженером:
curl -s localhost:8080/metrics | grep -E 'bvk_(ratelimit_wait|telegram_call|operation|ticket_relay)'
```

Что смотреть:

- `bvk_operation_s_max{label="create_topic"}` — сколько реально занимает подготовка
  топика; на моке это 5,6 с, из них ~3,1 с наш собственный интервал.
- `bvk_ratelimit_wait_ms_max{label="sendMessage"}` — наша задержка. Должна быть
  около 3,1 с на группу и 1,1 с на личный чат. Если она больше, лимитер ждёт
  напрасно.
- `bvk_telegram_call_ms_max{label="createForumTopic"}` — реальная скорость
  Telegram. Если она близка к 250 мс из мока, базовая линия переносится на прод.
- `bvk_ticket_relay_ms_max{label="client_message"}` и `...{label="team_message"}` —
  сколько сообщение идёт от записи до появления у другой стороны. Это то самое
  «медленно передаёт первые сообщения».

### Не выполнено и не подтверждено

- **Настоящий Telegram-пилот.** Сценарий: доступ новым аккаунтом; заявка с
  дополнением до взятия; обмен текстом и файлами вторым инженером отдела; имя,
  username и передача с «-»; закрытие с вложением и удалением; повторное открытие
  и старая кнопка; перезапуск во время копии и снятие доступа к копиям;
  Windows-служба с правами PostgreSQL, независимым носителем и внешним
  оповещением.
- **Нативный запуск Windows-службы** для бота и аналитики, ACL, домен, внешний
  HTTPS.
- **Внешнее размещение аналитики** и приёмка руководителем на реальных задачах.
- **Замеры работающего сервера.** Ориентир 10–40 заявок в день нагрузочным тестом
  не подтверждён.

### Технические ограничения

1. Лимиты Telegram: для группы — 20 сообщений в минуту, для чата — около одного в
   секунду. Обходить горутинами нельзя; при `429` повтор с `retry_after`.
2. Последний шаг удаления защищён общей блокировкой, сетевой вызов ограничен 5 с
   вместо 65 с; таймаут оставляет удаление для безопасного повтора.
3. Входящие обработчики последовательны: `/report`, выдача файла истории и `/bind`
   могут задержать применение следующих входящих во время HTTP и диска.
4. Четыре исходящих обработчика — ограниченная очередь: четыре долгие операции
   могут задержать пятую.
5. Большая история: список заявок и история читают данные целиком, планировщик
   обходит историю, аналитика пересчитывает полный снимок. SQL-пагинация и
   инкрементальная аналитика не сделаны.
6. Карантин inbox блокирует зависимые действия и удаление до разбирательства;
   автоматически объявлять update успешным небезопасно. Команда `/quarantine`
   даёт просмотр и снятие, но автоматического восстановления нет.
7. Неизвестный исход Telegram: если сервер принял сообщение, а ответ потерялся,
   повтор может дать дубль.
8. Файлы свыше 20 MiB не имеют независимой локальной копии, и такое завершение не
   должно разрешать удаление топика.
9. Завершение без топика не запускает копию; топики, закрытые передачей, в
   удаление последнего топика не включаются; исторические закрытия сохраняются.
10. Роль `dispatcher` и callbacks ожидания остаются в коде при упрощённых меню.
11. Модель `Button` знает только text, callback и url: цветные кнопки и custom
    emoji не реализованы. Карточки инженера — HTML с экранированием, обычная
    переписка без восстановления Telegram entities. Каталога локализации нет.
12. Автоматической ротации архивов и копий нет; разные пути не проверяются на
    разные физические диски; секреты в копию не входят; отдельной команды полного
    восстановления рабочего приложения нет.
13. Планировщик бота сохраняет старое `FirstResponseAt` после повторного открытия,
    а аналитика считает первый ответ заново по циклу, поэтому её категория «без
    ответа» может отличаться от старых напоминаний.
14. Exactly-once нет; длительный простой может привести к потере внешних updates.
    Webhook-режима, второго активного хоста и авто-failover нет.
15. Полнотекстового поиска и фильтров нет, только `/ticket ID`. Административных
    панелей и мониторинга нет.
16. Замена вложения редактированием пишет `media_edit_unsupported`, оставляет
    исходный файл и блокирует автодаление; сценария снятия блокировки нет.
17. Telegram запрещает `deleteMessage` для сообщений старше 48 часов; ошибка
    удаления не отменяет завершение.
18. Аналитика восстанавливает начальный отдел обратным обходом цепочки передач;
    повреждённая передача разрывает цепочку, а полностью отсутствующую передачу
    без противоречий обнаружить невозможно.
19. Мобильный Metabase располагает карточки в один столбец и прокручивает таблицы
    горизонтально; отдельной мобильной версии нет.
20. Вне границ: MAX, мониторинг инфраструктуры, параллельные связанные заявки,
    аварии и дежурства, теги администратора, новые отчёты и фильтры, dashboards
    автоматизации, ротация копий, второй хост, failover, репликация PostgreSQL,
    резервирование архивных файлов, каталог локализации, Embedding и публичные
    ссылки, SQL-редактор для руководителей.

## 17. Поведение на путях отказа

Классификация проверена табличным тестом на настоящей БД
(`internal/telegram/failure_classification_test.go`): одна заявка прогоняется через
каждый путь, и для каждого проверяется, что `runOperation` возвращает `nil` (то есть
цикл воркера **не разваливается** от удалённой ошибки), какое состояние получает
операция, уходит ли она в повтор, считается ли для `/ready`, и что в причине **не
утекает токен**.

| Путь отказа | Что отвечает Telegram | Состояние операции | Повтор | `/ready` |
|---|---|---|---|---|
| Клиент заблокировал бота | `403 Forbidden` | `failed` | нет, постоянно | 503 |
| Слишком много запросов | `429` + `retry_after` | `pending` | да, **через указанную паузу** | 200 |
| Неверный токен | `401 Unauthorized` | `failed` | нет, постоянно | 503 |
| Telegram недоступен | нет ответа / сеть | `pending` | да, с нарастающей паузой | 200 |
| Сбой на стороне Telegram | `500` | `pending` | да, с нарастающей паузой | 200 |
| Редактирование удалённой карточки | `400 message/thread not found` | считается **успехом** | не требуется | 200 |
| База данных недоступна | — | `bvk_updates` не завершается | повтор без карантина | 503 «database unavailable» |

Ключевые правила, которые из этого следуют:

- **Медленный `retry_after` соблюдается буквально.** Запрос с `retry_after: 45`
  планирует повтор примерно через 45 с, а не через собственную паузу 1 с, иначе бот
  долбит API, который прямо попросил остановиться.
- **Постоянные ошибки (`4xx`, кроме `429`) сразу уходят в `failed`** и попадают в
  счётчик `/ready`. Живая заявка с такой ошибкой **остаётся видимой** — автоуборка её
  не трогает (см. §16).
- **Недоступная БД никогда не превращает действие в карантин**: update остаётся
  незавершённым и повторяется, поэтому деловое действие не теряется.
- **Правка карточки, которой уже нет, — не ошибка.** Это нормальное следствие
  удаления завершённых топиков (см. §16).
- **Токен не попадает в сохранённые причины ошибок** — проверено тестом.

Проверка на живой сети: при блокировке Telegram бот **не падает**, каждые 65 с
повторяет `getUpdates`, `/ready` честно отдаёт `503 Telegram polling unavailable`, а
`/live` остаётся `200`. Как только сеть отпускает, опрос восстанавливается сам без
перезапуска.

**Важно перед перезапуском.** Старт выполняет `getMe`, затем для каждого отдела
`getChat` и `getChatMember`. Это до десяти сетевых вызовов **до** запуска
обработчиков, и при недоступном Telegram любой из них валит запуск целиком:
процесс завершится с ошибкой и бот **не поднимется вообще**. Поэтому:

- если бот уже работает, а сеть моргает — **не перезапускать**: он сам возобновит
  опрос, как только сеть отпустит;
- перед перезапуском убедиться, что Telegram доступен:
  `curl -s -o /dev/null -w '%{http_code}\n' https://api.telegram.org` должен вернуть
  **200**, а не `000`;
- при `000` перезапуск только ухудшит состояние: вместо работающего, но не
  опрашивающего процесса не будет никакого.

Отдельная шероховатость: при сетевой недоступности ошибка старта выглядит так же,
как при неверном токене или отсутствии прав. Оператору стоит проверить обычную
связность прежде, чем искать проблему в конфигурации.
