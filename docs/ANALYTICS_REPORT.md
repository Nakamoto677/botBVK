# Отчёт: аналитика поддержки BVK на Metabase

**Последующее локальное внедрение:** панель и два тестовых аккаунта запущены
на Mac по новому указанию пользователя. Настоящий импорт и основные переходы
проверены; ошибки API/служебной доставки исправлены. Актуальный доступ и команды —
[LOCAL_ANALYTICS.md](LOCAL_ANALYTICS.md). Ниже сохранён исходный отчёт разработки.

Дата: **13 октября 2026**, часовой пояс Asia/Irkutsk.
Ветка: `codex/metabase-analytics`.
Основание: приложенный пользователем `/Users/analdestroyer228/Downloads/PLAN.md`.
Финальное уточнение пользователя: **«Пока только подготовить код и инструкции»**.
Работа выполнена в этом объёме; размещение сервера отложено.

## Что сделано

1. Добавлен самостоятельный `cmd/bvk-analytics`, использующий календарь и пороги
   бота. Запускает пересчёт сразу и каждую минуту, поддерживает `-once` и отдельную
   административную `-migrate`. Токен Telegram не требуется.
2. Создана добавочная схема PostgreSQL `analytics`. Процесс пакетно читает
   согласованный снимок заявок, событий, метаданных сообщений и справочников,
   восстанавливает историю и атомарно публикует результаты. Ошибка не уничтожает
   предыдущий снимок; блокировка исключает конкурирующие публикации.
3. Реализованы циклы создания/повторного открытия, назначения, передачи, ожидание,
   закрытия и отмены. Автор исторического закрытия берётся из события; повторное
   открытие не удаляет прошлое закрытие. Отдел фиксируется исторически, исполнители
   из текущего состояния не подставляются вместо неизвестных.
4. Первый ответ считается только по подтверждённой доставке исходного публичного
   сообщения данного цикла. Исключены неудачные отправки, служебный ввод,
   исправления и поздняя доставка старого цикла. Отдел ответа соответствует
   доставке, а не последующему закрытию.
5. Рассчитаны календарные/рабочие сроки, ожидание и срок без ожидания. Добавлены
   признаки внимания и рабочие длительности ожидания, версии/свежесть снимка,
   маркировка пробелов истории. Неизвестные длительности остаются NULL.
6. Подготовлены **48 SQL-карточек**, раскладка вкладок **«Обзор», «Сотрудники»,
   «Требуют внимания»**, точные списки показателей и карточка заявки с циклами
   и результатами. Фильтры отделов/сотрудников/компаний используют имена из
   справочников, передавая стабильные ID. Настроены явные переходы KPI и колонок
   сотрудников; SQL-карточкам не требуется автоматическое раскрытие Metabase.
7. Создан воспроизводимый OSS API-импортер: повторное обновление без дубликатов
   при сохранённом state, вкладки/раскладка/фильтры/ссылки, предпросмотр и проверка
   запросов. Пароли и токены не сохраняются в state. Контракт сверён с исходным
   API Metabase v0.64.1.
8. Подготовлены Windows/NSSM-службы, Caddy/HTTPS, ограниченные PostgreSQL-роли,
   отдельная база настроек Metabase, резервное копирование и безопасное
   восстановление в новую БД, инструкция ручного переключения второго сервера.
   Закреплены версии компонентов; установщик требует заполненных проверенных
   SHA256 и создаёт остановленные службы.
9. Добавлены аудит метаданных исходной БД, автоматические проверки и нагрузочный
   сценарий. Обновлены общий PLAN, README и Windows-сборка аналитики.

Сценарии Telegram и рабочие записи не менялись. Переписка и вложения не публикуются
в аналитике. Все обращения к PostgreSQL в этой работе выполнялись на отдельном
временном кластере и синтетических данных.

| Проверка | Результат |
|---|---|
| `go test -race -count=1 ./...` с `TEST_DATABASE_URL` и `TEST_BACKUP_TOOLS=1` | Прошёл весь проект, настоящий dump/restore и сквозной цикл архивирования |
| Аналитические регрессии | Прошли повторные циклы/разные закрывшие, передачи, назначения, отмена, ожидание, праздники/выходные, старые/неудачные доставки, пробелы и пустые данные |
| PostgreSQL публикация | Предыдущий снимок сохранён при принудительном сбое COPY; после повторного запуска обновление восстановлено |
| Согласованность | Проверены стабильное чтение источника, MVCC-чтение предыдущего снимка и блокировка второго расчётчика |
| SQL Metabase | Все 48 запросов выполнены с фильтрами и без; KPI совпали с количеством строк детализации; баланс очереди сошёлся с передачами |
| Исторические выборки | Последнее закрытие выбрано до фильтра участника; ответ IT остался в IT после закрытия в 1С |
| Права | Читатель видит только аналитику, не пишет; расчётчик читает нужный источник, не меняет его; provision/check-privileges прошли |
| Импортер | Контрактные тесты прошли: повторный импорт, три вкладки, именные фильтры, ссылки, отсутствие секрета в state |
| Процесс без Telegram | Ограниченная роль опубликовала два снимка с минутным интервалом; SIGTERM дал корректное завершение |
| `go vet ./...` | Прошёл |
| Windows amd64 cross-build | Бот и аналитика собраны; нативный запуск Windows не выполнялся |

Основные воспроизводимые команды:

```sh
TEST_DATABASE_URL='postgres://USER@HOST:PORT/TEST_DB?sslmode=disable' TEST_BACKUP_TOOLS=1 go test -race -count=1 ./...
TEST_DATABASE_URL='postgres://USER@HOST:PORT/TEST_DB?sslmode=disable' TEST_ANALYTICS_LOAD=1 go test -count=1 -run TestFiveYearRefresh -v ./internal/analytics
go vet ./...
python3 -m unittest discover -s analytics/metabase -p 'test_*.py'
python3 analytics/metabase/import.py --database-id 1 --dry-run
GOOS=windows GOARCH=amd64 go build -trimpath -o bin/bvk-analytics.exe ./cmd/bvk-analytics
```

Интеграционные проверки аналитики сами создают отдельную временную БД; для этого
тестовое подключение должно иметь CREATEDB. Не задавайте производственный DSN
для полного набора тестов проекта.

## Производительность

Синтетическая история: **73 000 заявок, 438 000 событий, 73 000 сообщений** —
40 заявок в день в течение пяти лет, по шесть фактов и одному сообщению.
Полный проход **чтение PostgreSQL → расчёт → публикация** занял **3,03 секунды**
на Apple M5 с локальной PostgreSQL 18.6. Отдельный расчёт в памяти — около
**0,48 секунды**. Это одиночные измерения на разработческой машине; объём
реальной переписки и Windows-сервер нужно измерить при внедрении.

## Что проверить при развертывании

В соответствии с уточнением пользователя эти действия сейчас не выполнялись:

- Аудит копии рабочей БД и сверка нескольких настоящих заявок. Найденные
  локальные копии относятся к `bvk_test`, поэтому не являются рабочей историей.
- Настоящий запуск/импорт Metabase, визуальный вид, dropdown-фильтры, переходы,
  права двух руководителей и выгрузка. Моки проверяют контракт импортера,
  но не заменяют интерфейсный пилот.
- Нативные Windows/PowerShell/NSSM, ACL, домен и внешнее HTTPS с телефона/ПК.
- Восстановление настоящей прикладной БД Metabase и проверка входа/дашбордов
  на восстановленной панели. Проверка archive-list скриптом не равна этому тесту.

Ограничения истории: старый `created` не хранит начальный отдел; он восстанавливается
по цепочке событий. Незаметно отсутствующую передачу восстановить достоверно нельзя.
После повторного открытия аналитика считает первый ответ нового цикла, а старое
поле бота может хранить прежний ответ; напоминания бота не изменялись.
Неполные записи маркируются. График и распределения остаются SQL-визуализациями;
точный список открывается через KPI с выбранными фильтрами. Между независимыми
запросами Metabase во время публикации возможны соседние целые снимки, поэтому
строгую ручную сверку следует проводить при остановленном расчётчике.
