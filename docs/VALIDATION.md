# Проверка актуального плана — 12 октября 2026

Автоматические проверки выполняются на macOS arm64, Go 1.26.5, с отдельным PostgreSQL 17 в Docker (`bvk-transparent-test`, порт 55433). Рабочая база на порту 55432 не менялась. Telegram проверяется HTTP-сервером; токен настоящего бота не использовался.

## Автоматические результаты

- `go test -race -count=1 ./...` с `TEST_DATABASE_URL` и `TEST_BACKUP_TOOLS=1`: прошли оба полных прогона, включая финальные защиты inbox, прежних кнопок и точного топика. После последнего изменения команды отмены повторно прошли тесты Telegram.
- `go vet ./...`: прошёл.
- `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath`: прошёл, получен `bin/bvk-windows-amd64.exe`.
- Настоящие `pg_dump` и `pg_restore` PostgreSQL 17 выполнялись через Docker в отдельные временные базы. Проверяется не только наличие дампа, но восстановление, копии вложений и SHA-256.

## Покрытые сценарии

- Отмена без причины, точные кнопки подтверждения, отказ, повторное подтверждение, завершённая заявка, устаревшая кнопка нового сценария и прежнего цикла.
- Сохранение служебного сценария после пересоздания обработчика; ошибка сохранения оставляет ввод; ошибка очистки не откатывает отмену; повтор восстанавливает очистку.
- Изоляция вспомогательных сообщений по пользователю, чату, топику и сценарию; конкурентная очистка не дублирует операции. Удаление подсказки не зависит от наличия тикета.
- Обычные ответы и вложения инженера отдела, включая другого исполнителя, без Reply или предварительной кнопки. Очередь и устаревший топик не пересылаются.
- Прежние внутренние заметки сохраняют видимость; служебные вложения архивируются отдельно; служебный ввод не превращается в публичный ответ.
- Доступ, одна открытая заявка, конкурентное назначение, откаты, дедупликация входящих сообщений, FIFO outbox и восстановление аренды.
- Сквозной цикл на настоящей БД: регистрация → очередь → сообщение до назначения → взятие → топик → передача → очередь другого отдела → новое взятие → ответ → закрытие с файлом → автоматическая копия и проверка восстановления → удаление → история → повторное открытие → новый топик → отмена → проверенная копия и удаление.
- Исторические удаления без явного нового завершения отключаются миграцией; новая операция привязана к ключу завершения и точному старому топику, новое назначение не затрагивается.
- Отсутствующий топик считается успешно удалённым. Ошибки Telegram сохраняют повтор удаления; архивные ошибки могут восстанавливаться автоматически, исчерпанные попытки архивирования сбрасываются при повторе.
- Поздняя правка прежнего текста и неподдерживаемая замена медиа блокируют удаление до сохранной копии. Необработанный inbox блокирует подготовку; окончательная проверка под блокировкой согласована с записью новых updates.
- CSV разделяет закрытия инженером и отмены клиентом; рабочий календарь и обычные напоминания сохраняются.

## Надёжность и основные сценарии — 13 октября 2026

Реализация по `AGENT_RELIABILITY_UX.md`, ветка `codex/reliability-ux`.
Предыдущие незакоммиченные изменения сохранены; рабочая БД не использовалась.

Тестовый PostgreSQL **18.6 (Homebrew)** создан отдельно в
`/private/tmp/bvk-reliability-pg`, слушал **127.0.0.1:56439**.
Тесты использовали отдельные схемы и временные базы; настоящие `pg_dump` и
`pg_restore` — 18.6. Эту проверку не следует смешивать с прежними прогонами на 17.

Проверенные группы:

- Постоянный отказ Telegram при прямой служебной отправке: polling продолжает
  принимать updates, независимый клиент создаёт форму, зависимый update остаётся
  заблокированным. Повторы, причина и карантин хранятся в БД; карантин не отмечен
  как успешная обработка и блокирует архив. Ошибка БД не расходует повторы.
- Порядок сообщений одной заявки, включая команды закрытия в очереди и
  сохранённый служебный ввод. Очередь экранов использует человека, нажавшего
  callback, а не автора-бота. Пустая разметка и нулевой топик не уходят в личный чат.
- Длинные тексты с emoji/ZWJ/комбинируемыми символами, максимальный текст и
  подпись с именем автора, сохранение подтверждённой части после частичного
  отказа и создания нового Worker. Форма явно сокращает только предпросмотр.
- Две формы, старые поколения и legacy payloads, отмена, успешная подача,
  замена описания без потери файла, новый Adapter после сохранения черновика.
  Атомарная подача, двойной submit, rollback при конфликте вложения,
  сохранность legacy-черновика и результатов миграции.
- Реальный PostgreSQL `NextOperation` с первой попыткой `1`: одно первое и одно
  итоговое уведомление инженеру; промежуточные повторы не создают спам.
- Запрет клиенту `service`/`internal`, их текстов, revisions, имён и файлов;
  запрет чужого вложения. Проверка SHA-256 и архивного корня при локальной выдаче.
- Публичные исправления до/после доставки в правильной последовательности;
  поздний повтор исходного ответа после исправления не отправляет старый текст.
- Последняя из нескольких передач, «-» → «Без комментария», служебная кнопка
  файла и прекращение старого контекста после повторного открытия.
- 23 доступные заявки на трёх страницах без дублей/пропусков, чужая заявка
  скрыта, отозванные права проверяются на следующем callback.
- Сквозной цикл на отдельной БД: регистрация/одобрение → атомарная заявка с
  файлом → дополнения до взятия → топик → ответ и исправления → передача со
  служебным файлом → новое взятие → закрытие → настоящая проверенная копия
  и удаление → карточка и локальный файл → повторное открытие → новый топик
  → отмена → проверенная копия и удаление. Telegram заменён HTTP-моком.

Команды итоговой проверки:

```sh
TEST_DATABASE_URL='postgres://postgres@127.0.0.1:56439/postgres?sslmode=disable' \
  TEST_BACKUP_TOOLS=1 go test -race -count=1 ./...
go vet ./...
GOOS=windows GOARCH=amd64 go build \
  -o /private/tmp/bvk-reliability-windows-amd64.exe ./cmd/bvk
git diff --check
```

**Итоговый результат:** все четыре команды прошли после последних изменений.
Полный `go test -race -count=1 ./...` выполнен с обеими тестовыми переменными:
PostgreSQL и реальный dump/restore не пропущены. Пакет сквозного цикла
`internal/integration` завершился за 160,858 секунды. В отдельных файлах
`reliability_test.go` добавлены 17 новых регрессий; существующие UI/сервисные и
сквозной тесты обновлены под новые контракты. Windows-бинарник проверен как
PE32+ x86-64. Созданный тестовый сервер после проверки остановлен.

Совместимость: миграция `006_reliability` добавляет поля inbox, состояние
черновика, подтверждённые части и индексы дедупликации. Старые записи, архивы,
прежние сообщения и политики удаления сохраняются. Legacy callbacks формы
дают безопасный ответ, legacy-черновик привязывается при `/form`.

Не выполнены: настоящий Telegram-пилот двумя аккаунтами и нативный запуск
Windows-службы. Ограничения: неизвестный сетевой исход Telegram допускает
повторную отправку; любой нерешённый inbox консервативно блокирует подтверждение
полноты архива; новый интерфейс управления карантином не добавлен. Полнотекстовый
поиск, административные панели и мониторинг не входят в задачу.

## Аудит серий сообщений, скорости и блокировок — 14 октября 2026

Ветка `codex/system-audit`. Изолированный PostgreSQL 18.6 на
`127.0.0.1:57439`, каталог `/private/tmp/bvk-audit-20261014-pg`.
Рабочая БД и действующий Telegram-бот не использовались.

Добавлено **19 регрессионных тестов**: 9 в `telegram/burst_test.go`,
7 в `postgres/burst_test.go`, по одному для порядка блокировок сервиса,
изоляции аналитики и проверки копии до общей блокировки. Существующие тесты
формы и независимого polling адаптированы к накоплению текста и двум циклам.

Успешный полный итоговый прогон:

```sh
TEST_DATABASE_URL='postgres://postgres@127.0.0.1:57439/postgres?sslmode=disable' \
TEST_BACKUP_TOOLS=1 GOCACHE=/private/tmp/bvk-audit-go-cache \

```

Все пакеты прошли. PostgreSQL и настоящие `pg_dump`/`pg_restore` включены;
сквозной `internal/integration` — **130,102 с**. После последней локальной
доработки подавления устаревших подсказок альбома весь пакет `internal/telegram`
повторно прошёл с `-race -count=1` за **12,615 с**. Этот последний шаг не менял
сервис, миграции, архив или маршрутизацию.

Также успешно:

```sh

  go build -o /private/tmp/bvk-audit-windows-amd64.exe ./cmd/bvk

  go build -o /private/tmp/bvk-audit-analytics-windows-amd64.exe ./cmd/bvk-analytics

```

Диагностический `scripts/diagnose-locks.sql` выполнен в отдельной схеме
тестовой БД с последующим `ROLLBACK`. Синтетический замер выбора/подтверждения
100 сообщений при 10 000 завершённых строках inbox — **50,35 мс** без
Telegram и бизнес-обработки, не производственная задержка.

Первый вариант нового HTTP-мока long poll зависал при завершении, потому что
обработчик не читал тело HTTP-запроса перед ожиданием отмены. Исправлен сам мок;
последующие отдельный и полный race-прогоны успешны.
